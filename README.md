# pii-scan

Поиск персональных данных (152-ФЗ) в **MySQL**, **PostgreSQL** и
**ClickHouse**. Отвечает на один вопрос: в каких таблицах и полях лежат ПДн,
каких категорий и насколько можно доверять выводу.

Ничего не пишет в обследуемые БД, не передаёт данные по сети и не маскирует
поля — только находит и документирует.

| СУБД | Проверено вживую |
|---|---|
| MySQL / MariaDB | MySQL 8.4 |
| PostgreSQL | PostgreSQL 16, несколько схем в одной базе |
| ClickHouse | ClickHouse 24.8, HTTP и нативный протокол |

**На выходе — четыре файла в каталоге `out/`:**

| Файл | Назначение | Кому |
|---|---|---|
| `summary.md` | только уверенные находки, строка на таблицу | владельцу системы, руководителю |
| `detailed.md` | все находки, включая пограничные, с основанием вывода | разработчикам |
| `registry.xlsx` | реестр с автофильтром: листы «Реестр», «Требует проверки», «Сводка» | в реестр ПДн, проверяющим |
| `findings.json` | полная выгрузка со всеми оценками | скриптам, для сравнения прогонов |

## Быстрый старт

Пять шагов от чистого сервера до отчёта. Подробности каждого — в разделах ниже.

```bash
git clone https://github.com/vehpbkrby/pii-scan.git && cd pii-scan
./install.sh                          # проверит docker, соберёт образ, поставит команду
$EDITOR .env                          # пароли учётной записи pii_reader
$EDITOR config/config.yml             # адреса баз
pii-scan --dry-run                    # проверка связи и прав, данные не читаются
pii-scan                              # полный прогон, отчёты в out/
```

Учётную запись с правом `SELECT` нужно выдать заранее — см.
[Учётные записи в БД](#учётные-записи-в-бд).

## Подготовка

### Учётные записи в БД

Сканеру нужен **только SELECT**. Наличие прав на запись блокирует запуск с
кодом возврата `3` — это защита от прогона под административной учёткой на
проде. Обойти можно ключом `--allow-rw`; в отчёте останется отметка, что
источник сканировался не в режиме только чтения.

#### MySQL

```sql
CREATE USER 'pii_reader'@'10.0.0.%' IDENTIFIED BY 'СЛОЖНЫЙ_ПАРОЛЬ';
GRANT SELECT ON *.* TO 'pii_reader'@'10.0.0.%';
```

Чтобы обследовать не весь сервер, а отдельные базы:

```sql
GRANT SELECT ON crm.* TO 'pii_reader'@'10.0.0.%';
GRANT SELECT ON billing.* TO 'pii_reader'@'10.0.0.%';
```

| | |
|---|---|
| **Что читается** | `information_schema.TABLES` и `.COLUMNS` — структура; `SHOW GRANTS FOR CURRENT_USER()` — проверка режима только чтения; `SELECT` — выборка значений |
| **Что не нужно** | `PROCESS`, `SUPER`, `RELOAD`; отдельные привилегии на `information_schema` |
| **Особенность** | MySQL показывает в `information_schema` только объекты, на которые есть хоть какие-то права. Выдав SELECT лишь на одну базу, вы ограничите охват — остальные сканер не увидит |

#### PostgreSQL

```sql
CREATE ROLE pii_reader LOGIN PASSWORD 'СЛОЖНЫЙ_ПАРОЛЬ';
GRANT CONNECT ON DATABASE имя_базы TO pii_reader;
GRANT USAGE ON SCHEMA public TO pii_reader;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO pii_reader;
ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT SELECT ON TABLES TO pii_reader;
```

| | |
|---|---|
| **Права выдаются** | в каждой обследуемой базе отдельно: в PostgreSQL нет межбазовых запросов, поэтому сканер открывает своё подключение на каждую базу |
| **Что читается** | `pg_database`, `pg_class`, `pg_namespace`, `pg_attribute`, `pg_index` — структура; `col_description()` — комментарии к полям; `information_schema.role_table_grants` и `pg_roles` — права |
| **Размер таблиц** | из `pg_class.reltuples` — оценки планировщика. `COUNT(*)` не выполняется |
| **Считается записью** | `SUPERUSER`, `CREATEDB`, `CREATEROLE` |
| **Имена в отчёте** | трёхуровневые, `база.схема.таблица` — иначе `public.clients` и `billing.clients` слились бы в одну строку |

Если `databases` в конфиге не задан, сканер перечислит все базы, к которым
разрешено подключаться, и обойдёт их по очереди.

#### ClickHouse

```sql
CREATE USER pii_reader IDENTIFIED WITH sha256_password BY 'СЛОЖНЫЙ_ПАРОЛЬ'
    SETTINGS readonly = 2;
GRANT SELECT ON *.* TO pii_reader;
```

| | |
|---|---|
| **Почему `readonly = 2`, а не `1`** | сканер выставляет своим запросам `max_execution_time` и `max_threads`, чтобы не нагружать сервер. При `readonly = 1` сервер запретит менять настройки и запросы упадут |
| **Что читается** | `system.tables` и `system.columns` (видны объекты, к которым есть доступ), `system.settings` — проверка readonly, `SHOW GRANTS`, `SELECT` |
| **Что не нужно** | `ADMIN`, `SYSTEM`, `INTROSPECTION` |

### Подключение по сети

Сканер подключается к СУБД обычным сетевым соединением — БД могут стоять на
других серверах, локально ничего разворачивать не нужно.

| СУБД | Порт | Протокол | Драйвер |
|---|---|---|---|
| MySQL / MariaDB | 3306 | родной MySQL | PyMySQL (запасной — mysql-connector) |
| PostgreSQL | 5432 | родной | psycopg 3 (запасной — psycopg2) |
| ClickHouse | 8123 (HTTPS — 8443) | HTTP | clickhouse-connect |
| ClickHouse | 9000 (TLS — 9440) | нативный | clickhouse-driver |

Драйвер ClickHouse выбирается **по указанному в конфиге порту**, оба пакета
есть в образе.

TLS включается флагом `secure: true`. При необходимости укажите корневой
сертификат `ssl_ca` — путь **внутри контейнера**, файл положите в `config/`.
`ssl_verify: false` отключает проверку сертификата.

**Что важно в Docker:**

| Ситуация | Что делать |
|---|---|
| БД на другом сервере | ничего, работает как есть |
| БД в docker-сети | `PII_NETWORK=имя_сети pii-scan` |
| БД на 127.0.0.1 того же хоста | из контейнера этот адрес указывает на сам контейнер: раскомментируйте `network_mode: host` в `docker-compose.yml` либо используйте `host.docker.internal` с `extra_hosts: ["host.docker.internal:host-gateway"]` |
| Не резолвится имя хоста | пропишите адреса через `extra_hosts` в compose-файле |

В интернет утилита не ходит: HTTP-клиента в коде нет, модели NER загружаются
с диска. Контейнеру достаточно доступа к портам обследуемых СУБД.

## Установка

Способа два, это **альтернативы**, а не шаги подряд. Результат одинаковый:
собранный образ, каталоги `config/` и `out/`, готовые к правке `config.yml`
и `.env`.

| Способ | Когда выбирать |
|---|---|
| [Установщик](#способ-1-установщик) | по умолчанию: сам проверит окружение, соберёт образ и поставит команду `pii-scan` |
| [Вручную](#способ-2-вручную) | нельзя ставить команду в систему, свой процесс сборки, либо образ приезжает готовым файлом |

Общий шаг один:

```bash
git clone https://github.com/vehpbkrby/pii-scan.git && cd pii-scan
```

### Способ 1: установщик

```bash
./install.sh
```

Скрипт проверит docker и место на диске, создаст `config/` и `out/`, положит
`config.yml` и `.env` из примеров (`.env` с правами 600), соберёт образ и
поставит команду `pii-scan` — обёртку над `docker run` с нужными томами,
`--user` и выделением терминала под индикатор выполнения.

| Ключ | Что делает |
|---|---|
| `./install.sh` | образ с NER (276 МБ) |
| `./install.sh --slim` | образ без NER (164 МБ) — для закрытого контура |
| `./install.sh --systemd weekly` | плюс регулярный прогон по расписанию systemd |
| `./install.sh --skip-build` | не собирать образ (уже загружен из файла) |
| `./install.sh --ca-cert ПУТЬ` | добавить корневой сертификат в сборку |
| `./install.sh --uninstall` | убрать команду и юниты (образ и отчёты остаются) |

Команда ставится в `/usr/local/bin`, если есть root или беспарольный sudo,
иначе в `~/.local/bin`.

Запускайте установщик **от своего пользователя**, а не из-под `sudo su`:
сканировать вы будете от себя, и созданный root-ом каталог `out/` окажется
недоступен для записи. Если всё же ставили от root, установщик сам вернёт
`config/`, `out/` и `.env` владельцу каталога проекта.

### Способ 2: вручную

То же самое тремя командами. Команда `pii-scan` при этом не появится —
запускать придётся через `docker run` или `docker compose`, см.
[Запуск без установщика](#запуск-без-установщика).

```bash
mkdir -p config out && cp config.example.yml config/config.yml   # 1. каталоги
cp .env.example .env && chmod 600 .env                           # 2. пароли
docker build --build-arg WITH_NLP=1 -t pii-scan:full .           # 3. образ
```

### Варианты образа

```bash
docker build -t pii-scan:slim .                          # 164 МБ, только regex
docker build --build-arg WITH_NLP=1 -t pii-scan:full .   # 276 МБ, + NER
```

Размеры измерены на Ubuntu 25.10, Docker 28.2. `docker compose` собирает
вариант из переменной `WITH_NLP` в `.env` (по умолчанию — с NER).

| | |
|---|---|
| **Когда брать slim** | закрытый контур: нет моделей, не придётся объяснять безопасникам лишние 500 МБ весов. NER при этом выключается с записью в лог |
| **База образа** | `python:3.10-slim`. Не случайность: `natasha` тянет `pymorphy2`, который использует `inspect.getargspec`, удалённый в Python 3.11 |
| **Модели NER** | `navec` и `slovnet` упакованы внутрь пакета `natasha` и ставятся при сборке. В рантайме интернет не нужен: инференс идёт локально на CPU |

### Частные случаи установки

#### install.sh не видит docker

Две самые частые причины:

**Демон не запущен.** `systemctl enable docker` только прописывает автозапуск
при загрузке, но сам сервис не поднимает:

```bash
sudo systemctl start docker
```

**Группа выдана, но не применилась.** `usermod -aG docker` меняет базу групп,
однако уже запущенная сессия свой список групп не перечитывает:

```bash
newgrp docker                 # применить в текущей сессии
sg docker -c ./install.sh     # либо сразу запустить установку
```

Либо выйти из системы и зайти заново. Проверить, что обе причины закрыты:

```bash
systemctl is-active docker && id -nG | tr ' ' '\n' | grep -x docker && docker info >/dev/null && echo ок
```

Установщик различает эти случаи и подсказывает нужную команду.

#### Корпоративный TLS-инспектор

Признак — сборка падает так:

```
[SSL: CERTIFICATE_VERIFY_FAILED] certificate verify failed:
self-signed certificate in certificate chain
ERROR: No matching distribution found for wheel
```

Трафик разбирает корпоративный TLS-инспектор: он подменяет сертификат
pypi.org своим. Сервер этому корню доверяет, а контейнер при сборке — ещё
нет, у него собственное хранилище. Передайте связку сертификатов хоста:

```bash
./install.sh --ca-cert /etc/ssl/certs/ca-certificates.crt
```

Установщик положит её в контекст сборки как `ca-cert.crt` (файл в
`.gitignore`), образ добавит сертификат в системное хранилище и укажет его
pip через `PIP_CERT` — pip проверяет сертификаты по связке certifi, а не по
системному хранилищу, поэтому одного `update-ca-certificates` мало.

Если PyPI закрыт полностью, а внутреннее зеркало есть:

```bash
./install.sh --pip-index https://nexus.corp/repository/pypi/simple --trusted-host nexus.corp
```

При сборке вручную — те же аргументы:

```bash
docker build --build-arg WITH_NLP=1 --build-arg PIP_INDEX_URL=... --build-arg PIP_TRUSTED_HOST=... -t pii-scan:full .
```

#### Сервер без доступа в интернет

Сборка образа — единственный шаг, которому нужен интернет. Соберите образ на
машине с доступом и перенесите файлом:

```bash
docker build --build-arg WITH_NLP=1 -t pii-scan:full .     # там, где есть интернет
docker save pii-scan:full | gzip > pii-scan-full.tar.gz
```

```bash
gunzip -c pii-scan-full.tar.gz | docker load               # на закрытом сервере
./install.sh --skip-build
```

## Запуск

### Первый прогон

**1. Пароли** — в конфиге их быть не должно, только ссылки `${VAR}`:

```bash
$EDITOR .env
```

```
MYSQL_PWD=пароль_учётки_pii_reader
CH_PWD=пароль_учётки_pii_reader
```

**2. Что обследуем** — адреса, учётные записи, при необходимости фильтры баз
и таблиц:

```bash
$EDITOR config/config.yml
```

Минимально достаточно этого:

```yaml
sources:
  - name: prod-mysql
    type: mysql
    host: 10.0.0.10
    user: pii_reader
    password: ${MYSQL_PWD}
```

Список таблиц перечислять не нужно — сканер сам прочитает структуру.
Несколько источников просто перечисляются в том же списке:

```yaml
sources:
  - name: prod-mysql
    type: mysql
    host: 10.0.0.10
    user: pii_reader
    password: ${MYSQL_PWD}

  - name: prod-postgres
    type: postgres
    host: 10.0.0.15
    user: pii_reader
    password: ${PG_PWD}
    databases: [shop]

  - name: prod-clickhouse
    type: clickhouse
    host: 10.0.0.20
    port: 9000
    user: pii_reader
    password: ${CH_PWD}
```

**3. Сухой прогон.** Читается только схема: имена таблиц, полей и
комментарии. Ни одна строка данных не читается, нагрузки практически нет.

```bash
pii-scan --dry-run
```

Так проверяются связь, права и охват, и уже видны поля, названные явно. **На
прод всегда заходите с этого.**

**4. Полный прогон** — с чтением выборки значений:

```bash
pii-scan
```

**5. Отчёты** — в каталоге `out/`. Имена файлов постоянные, каждый прогон их
перезаписывает. Две оговорки:

* с `--formats xlsx` (или любым неполным списком) остальные файлы **не
  обновляются и не удаляются** — в каталоге останутся отчёты прошлого прогона
  со старой датой;
* чтобы сохранить историю, копируйте `out/` с датой в имени. Сравнение
  `findings.json` между прогонами показывает, что появилось нового.

### Что видно во время работы

```
13:20:41 INFO    pii-scan 0.2.0 | конфиг: /config/config.yml | источников: 2 | режим: выборка значений
13:20:41 INFO    Источник 'prod-mysql': таблиц 286, к обследованию 12, по образцу 274
prod-mysql [████████░░░░░░░░░░░░░░░░] 59/286  21% · осталось ~4 с  big.orders_2020_11
```

Первая строка называет **версию работающего образа** — с неё начинается любая
диагностика, см. [Диагностика](#диагностика). По завершении в консоль
выводится сводка: сколько таблиц с ПДн и сколько полей требует проверки.

Полоса прогресса появляется, только когда вывод идёт в терминал. В cron,
systemd или `docker run` без `-t` вместо неё пишутся редкие отметки в журнал
(каждые 5 %). Управляется ключом `--progress auto|on|off`. Команда
`pii-scan`, поставленная установщиком, сама добавляет `-t`.

### Команды на каждый день

| Задача | Команда |
|---|---|
| **Инвентаризация, не трогая данные** | `pii-scan --dry-run` |
| **Полное обследование** | `pii-scan` |
| Только один источник | `pii-scan --only prod-mysql` |
| Ночной прогон с ограничением нагрузки | `pii-scan --pause-ms 200 --max-minutes 120` |
| Прогон в cron или systemd | `pii-scan --progress off --pause-ms 200 --max-minutes 120` |
| Быстрая прикидка без NER | `pii-scan --limit 100 --no-ner` |
| Точечно, с большой выборкой | `pii-scan --limit 20000 --only prod-mysql --details` |
| Разбивка по полям в консоли | `pii-scan --details` |
| Полная опись всех полей, включая чистые | `pii-scan --full-inventory --details` |
| Опись по одному источнику для разработчиков | `pii-scan --only prod-postgres --full-inventory --formats xlsx` |
| Упрощённый отчёт: без находок по одному имени поля | `pii-scan --confirmed-only` |
| С примерами значений (маскированными) | `pii-scan --details --examples` |
| Только реестр XLSX | `pii-scan --formats xlsx` |
| Отдать отчёты в другой каталог | `pii-scan --out /srv/audit/2026-08` |
| Искать одну категорию | `pii-scan --detectors names` |
| Несколько категорий | `pii-scan --detectors names,contacts` |
| Одно конкретное правило | `pii-scan --detectors snils` |
| Посмотреть доступные категории | `pii-scan --list-detectors` |
| Свежие записи вместо старых | `pii-scan --strategy tail` |
| Каждая таблица отдельно, без наследования | `pii-scan --no-grouping` |
| Ограничить темп запросов | `pii-scan --max-qpm 60` |
| Обследовать конкретную базу PostgreSQL | `databases: [shop]` в конфиге источника |
| ClickHouse по нативному протоколу | `port: 9000` в конфиге источника |

Три случая, где стоит пояснить выбор ключей:

**Точечная проверка редко заполненного поля.** Обычных 500 строк не хватает,
если поле заполнено в одной записи из ста. Сузьте охват через
`include_tables` в конфиге и поднимите лимит — глобально его поднимать
дорого.

**Быстрая прикидка на большой схеме.** `--limit 100 --no-ner` — минуты вместо
часов. Годится, чтобы понять масштаб, не годится как результат обследования.

**Прогон, который обязан закончиться.** `--max-minutes` завершает работу
штатно и сохраняет найденное; таблицы с вероятными ПДн обследуются первыми,
поэтому за отведённое окно в отчёт попадает главное.

### Запуск без установщика

Через compose:

```bash
PII_UID=$(id -u) PII_GID=$(id -g) docker compose run --rm scanner --config /config/config.yml --dry-run
```

Через `docker run` напрямую:

```bash
docker run --rm -t --user "$(id -u):$(id -g)" --env-file .env -v "$PWD/config:/config:ro" -v "$PWD/out:/out" pii-scan:full --config /config/config.yml --dry-run
```

| Аргумент | Зачем |
|---|---|
| `--user "$(id -u):$(id -g)"` | внутри образа пользователь с uid 10001; без этого `out/` окажется недоступен для записи. Права проверяются **до** сканирования, иначе многочасовой прогон терял бы результат на последнем шаге |
| `-t` | иначе не будет индикатора выполнения |
| `-v .../config:ro` | конфиг монтируется только на чтение, `out` — единственная точка записи |

### Что живёт между прогонами

Ничего. Постоянно работающей службы нет: контейнер создаётся в момент запуска
и удаляется сразу после завершения (`docker run --rm`).

| | Что это | Когда существует | Что потребляет |
|---|---|---|---|
| **Образ** `pii-scan:full` | файл на диске | постоянно, после сборки | 276 МБ диска |
| **Контейнер** | запущенный процесс | только во время сканирования | CPU и память на время прогона |

Между прогонами не остаётся ни фоновых процессов, ни открытых портов, ни
соединений с БД. Проверить:

```bash
docker ps | grep pii-scan
```

Пусто — ничего не выполняется. Есть строка — прогон идёт прямо сейчас.

Следствие: модели NER загружаются с диска при **каждом** запуске, около
полутора секунд, поэтому первая таблица обрабатывается дольше остальных.
`--no-ner` убирает и эту задержку.

Исключение одно — `./install.sh --systemd weekly`: контейнер запускает по
расписанию таймер systemd. Между запусками и там не работает ничего, висит
только сам таймер.

### Регулярные прогоны

```bash
./install.sh --systemd weekly
systemctl list-timers pii-scan.timer     # когда ближайший запуск
journalctl -u pii-scan.service           # как прошёл прошлый
```

Расписание задаётся в формате `OnCalendar`: `daily`, `weekly`,
`Mon *-*-* 03:00:00`. Прогон по таймеру идёт с ограничением нагрузки
(`--pause-ms 200 --max-minutes 120`) и без индикатора.

Отчёты перезаписываются на каждом прогоне, поэтому при работе по расписанию
складывайте их в архив. Добавьте в `/etc/systemd/system/pii-scan.service`
(знак процента в юнитах удваивается):

```ini
ExecStartPost=/bin/sh -c 'cp -a out "archive/$(date +%%Y-%%m-%%d)"'
```

### Остановка сканирования

| Ситуация | Что делать |
|---|---|
| Запущено в вашем терминале | `Ctrl+C` — docker передаёт сигнал внутрь контейнера, соединения с БД закрываются |
| Терминал закрыт, запускали из другой сессии | `docker ps --format "{{.ID}} {{.Image}} {{.Status}}" \| grep pii-scan`, затем `docker stop <ID>` |
| Ждать некогда | `docker kill <ID>` — `docker stop` даёт 10 секунд на завершение |
| Прогон по расписанию | `sudo systemctl stop pii-scan.service` |

**Отчёты за прерванный прогон не сохраняются.** Частичная выгрузка,
неотличимая с виду от полной, в реестре ПДн опаснее, чем её отсутствие. Если
прогон нужно ограничить по времени, но с результатом — используйте
`--max-minutes`.

#### Снять нагрузку с БД

Остановка контейнера рвёт соединение, но **уже выполняющийся запрос СУБД
может доработать до конца**: MySQL замечает обрыв не мгновенно.

MySQL — найти и снять:

```sql
SHOW PROCESSLIST;
```

```sql
KILL QUERY 12345;
```

Вместо `12345` — `Id` строки, где `User` = `pii_reader`. `KILL QUERY` снимает
запрос, оставляя соединение; `KILL` рвёт и соединение. Если запросов много,
соберите команды одним запросом и выполните результат:

```sql
SELECT CONCAT('KILL QUERY ', id, ';') FROM information_schema.processlist WHERE user = 'pii_reader';
```

ClickHouse:

```sql
SELECT query_id, user, elapsed, formatReadableSize(memory_usage), query FROM system.processes WHERE user = 'pii_reader';
```

```sql
KILL QUERY WHERE user = 'pii_reader' SYNC;
```

Обычно до этого не доходит: сканер выставляет своим запросам серверный
таймаут (параметр `query_timeout`, по умолчанию 15 секунд), поэтому
осиротевшие запросы отвалятся сами. Долгих тяжёлых запросов сканер не
создаёт — каждый это `SELECT … LIMIT 500` по одной таблице.

### Диагностика

**Начинайте с первой строки вывода — она называет версию образа:**

```
pii-scan 0.2.0 | конфиг: /config/config.yml | источников: 2 | режим: выборка значений
```

Образ не пересобирается сам, и «ключ не сработал» чаще всего означает, что
запущена прежняя сборка. Если примеры значений включены, следующая строка
скажет и об этом.

| Сообщение или симптом | Причина и решение |
|---|---|
| `каталог отчётов '/out' недоступен для записи` | контейнер запущен не под вашим uid — добавьте `--user "$(id -u):$(id -g)"`; либо `out/` принадлежит root после установки от root: `sudo chown -R $USER out config .env` |
| `переменная окружения MYSQL_PWD не задана` | нет `.env` или он не передан: `--env-file .env` |
| `учётная запись имеет права на запись` | нужна read-only учётка; осознанно обойти — `--allow-rw` |
| `Access denied for user` | неверный пароль или учётке не выдан `GRANT SELECT` |
| `не установлен драйвер MySQL` | запущен не тот образ; пересоберите: `./install.sh` |
| `Port 9000 is for clickhouse-client program` | образ старее версии с выбором драйвера по порту: `git pull && ./install.sh` |
| `PermissionError: '/app/pii_scan/__init__.py'` | образ собран на сервере с `umask 077`, файлы внутри нечитаемы: `git pull && ./install.sh` |
| Индикатор не появляется | нет `-t` у `docker run`, либо вывод перенаправлен в файл |
| Ключ вроде бы не работает, поведение прежнее | старый образ: сверьте версию из первой строки с `git log`, затем `git pull && ./install.sh` |
| В отчёте есть примеры значений, хотя их не просили | в `config/config.yml` осталась строка `examples_per_hit: 3` от прежних версий — уберите её или поставьте `0` |

[Коды возврата](#коды-возврата) — в справочнике.

## Отчёты

### Разбивка по полям

Сводка отвечает на вопрос «где искать», разбивка по полям — на «что именно и
на каком основании». Ключ `--details` выводит её в консоль:

```
crm.employees   (источник prod-mysql)
  Поле               Тип      Вид ПДн                         Основание                Совпало  Увер.
  -----------------  -------  ------------------------------  -----------------------  -------  -----
  full_name          varchar  ФИО, ФИО в тексте (NER)         имя поля, значения, NER  120/120  100%
  passport           varchar  паспорт РФ (серия и номер)      имя поля, значения       120/120  80%
  diagnosis          varchar  сведения о состоянии здоровья   только имя поля          0/120    75%
  passport_seria     char     паспорт РФ (серия и номер)      только имя поля          0/120    35%
```

| Колонка | Что означает |
|---|---|
| **Вид ПДн** | какие правила сработали |
| **Основание** | `значения` — распознаны сами данные; `NER` — имена найдены в свободном тексте; `имя поля` — сработало название или комментарий |
| **`только имя поля`** | содержимое читалось, но ни одно правило в нём ничего не узнало. Смотреть не на что — это вопрос к разработчикам, что в поле лежит |
| **Совпало** | сколько значений выборки подтвердились, из скольких содержательных |
| **Увер.** | итоговая оценка, см. [Уверенность и вердикты](#уверенность-и-вердикты) |

Поля вида `params::$.client.phone` — ключи внутри JSON-значения: видно не
только колонку, но и место внутри структуры.

То же самое в файлах, и для передачи разработчикам они удобнее:

| Файл | Что внутри |
|---|---|
| `registry.xlsx`, лист «Реестр» | строка на каждое поле с автофильтром: источник, СУБД, база, таблица, поле, тип, категория ПДн, вид ПДн, уверенность, основание, число совпадений |
| `registry.xlsx`, лист «Требует проверки» | пограничные находки — их и отдают на ручной разбор. Сверху подтверждённые содержимым, ниже держащиеся на одном названии поля |
| `detailed.md` | то же текстом, по таблицам |
| `findings.json` | для автоматической обработки |

### Полная опись полей

По умолчанию в отчёт попадают только поля, где что-то нашлось. Ключ
`--full-inventory` добавляет **все поля всех обследованных таблиц**, включая
чистые:

```
crm.employees   (источник prod-mysql)
  Поле               Тип      Вердикт           Вид ПДн                         Основание           Увер.
  -----------------  -------  ----------------  ------------------------------  ------------------  -----
  fio                varchar  ПДн               ФИО, ФИО в тексте (NER)         имя поля, значения  100%
  diagnosis          varchar  ПДн               сведения о состоянии здоровья   только имя поля     75%
  hired_at           date     требует проверки  дата рождения                   значения            50%
  id                 int      не обнаружено     —                               —                   —
  salary             decimal  не обнаружено     —                               —                   —
```

Это доказательство охвата: видно не только что нашли, но и что смотрели. В
реестре XLSX появляется лист **«Все поля»** — чистые залиты серым, находки
повышенной значимости оранжевым.

Поля со слабым сигналом помечаются отдельно: `слабый признак: СНИЛС (1 из 500)`.
Совпадение было, но до порога не дотянуло. Показывается счёт, а не процент —
у одного значения из пятисот доля округляется до «0 %», и вся информация
пропадает.

Опись заметно увеличивает объём отчётов, поэтому включается по требованию.

### Примеры значений

По умолчанию в отчёт **не выносятся**. Даже замаскированные
(`ив****@ex***e.com`), они оставляют длину, формат и первые символы, а отчёт
уходит разработчикам и внешним проверяющим.

```bash
pii-scan --details --examples      # три примера на находку
pii-scan --details --examples 5    # пять
```

Столбец появляется только вместе с ключом — пустым не стоит.

`--show-values` снимает и маскировку: отчёт становится полноценным носителем
ПДн со всеми вытекающими требованиями к его хранению.

### Упрощённый отчёт

Отчёт только из того, что подтвердило само содержимое:

```bash
pii-scan --confirmed-only
```

Поле, у которого в колонке «Основание» стоит `только имя поля`, в такой отчёт
не попадает. Число исключённых **объявляется в сводке** — иначе урезанный
отчёт неотличим от чистой базы:

```
! --confirmed-only: из отчёта исключено находок, у которых основание —
  одно имя поля: 5. Отчёт не является полным обследованием.
```

Вместе с `--full-inventory` такие поля остаются видимыми с пометкой
`исключено фильтром: паспорт РФ`.

**Коэффициент `name_boost` для этой задачи не подходит**, хотя и настраивается
(`--name-boost 0.2`). Он делает не то, чего от него ждут:

| Поле | boost 0.35 | boost 0.20 | boost 0 |
|---|---|---|---|
| `passport_seria` — только имя | 35 % проверка | 20 % нет | 0 % нет |
| `diagnosis` — только имя | **75 % ПДн** | **75 % ПДн** | **75 % ПДн** |
| `emergency_contact` — только имя | **75 % ПДн** | **75 % ПДн** | **75 % ПДн** |
| `city` — имя **и** 400/500 значений | 95 % ПДн | 80 % ПДн | **60 % проверка** |

Правила, где имя решает само (здоровье, родственники, место рождения),
коэффициенту не подчиняются, а подтверждённая значениями находка теряет от
него законно набранную уверенность. Понижать `name_boost` осмысленно только
чтобы сдвинуть границу для правил без собственного вывода по имени.

## Как работает поиск

### Каналы поиска

Свидетельств три, они **независимы**, и любого хватает самостоятельно.

| Канал | Что даёт | Пример |
|---|---|---|
| Имя колонки и комментарий | `+0.35` к оценке; для пяти правил — сразу вывод | `diagnosis` попадёт в отчёт, хотя диагноз словами распознать нечем |
| Значения из выборки | доля совпавших × вес правила | `rp_responsible` с фамилиями попадёт по значениям, хотя имя ни с чем не совпадает |
| NER по свободному тексту | факт присутствия ФИО или топонима | ФИО в поле `comment` найдутся, хотя поле называется нейтрально |

**Имя поля не участвует в отсеве.** Читаются и проверяются все колонки всех
таблиц; `field_23`, `col7`, `data` обследуются ровно так же, как `client_fio`.
Имя только усиливает вывод.

Что именно распознаётся по значениям:

| Способ | Правила |
|---|---|
| **По контрольной сумме** (ложных срабатываний практически нет) | СНИЛС, ИНН (10 и 12 знаков), полис ОМС, номер банковской карты |
| **По формату** (контрольной суммы нет) | паспорт РФ, загранпаспорт, водительское удостоверение, банковский счёт, почтовый индекс, отдельная фамилия или имя |
| **По значениям** | адрес электронной почты, телефон, адрес, ФИО целиком и по частям, дата рождения, код МКБ-10 |
| **По свободному тексту (NER)** | ФИО и населённые пункты в комментариях, описаниях, примечаниях |
| **Только по имени поля** | место рождения, национальность и подобное, сведения о родственниках |
| **Внутри JSON** | значение разбирается рекурсивно, каждый ключ становится виртуальной колонкой `payload::$.client.phone` |

Из 22 правил **19 работают по содержимому**: 17 разбирают само значение,
ещё 2 — распознают ФИО и топонимы в свободном тексте. Оставшиеся три —
место рождения, национальность и подобное, родственники — описывают данные,
у которых нет отличимой формы: «русский» неотличим от любого другого слова.
Значения в таких колонках всё равно проверяются остальными 19 правилами —
ФИО родственника найдётся правилом «ФИО», а не правилом «родственники».

Полный перечень правил печатает сам сканер:

```bash
pii-scan --list-detectors
```

### Что читается из таблицы

Не вся таблица. По умолчанию читается **500 строк** — этого хватает, чтобы
понять, что за данные лежат в колонке, и не хватает, чтобы уронить прод.
Полный скан не нужен: ПДн — свойство поля, а не отдельной строки.

| Что ограничивает | Параметр / ключ | По умолчанию |
|---|---|---|
| строк на таблицу | `sample_limit` / `--limit` | 500 |
| откуда берутся строки | `sample_strategy` / `--strategy` | `head_tail` |
| трафик на таблицу | `max_bytes_per_table` | 2 МБ |
| длина одного значения | `max_value_len` | 512 символов |
| значений на колонку для NER | `ner_values_per_column` | 50 |

**Половина выборки берётся с конца таблицы.** Чтение только «головы» —
систематическая слепая зона: поле, которое начали заполнять полгода назад, в
старых строках пусто, и сканер объявит его чистым. Поэтому по умолчанию
работает `head_tail`: 250 строк с начала и 250 с конца, по первичному ключу
или ключу сортировки. Без такого ключа (представление, таблица без PK)
читается только начало.

**Таблица меньше выборки читается целиком и один раз.**

**Широкая таблица читается мельче.** Ограничение идёт по трафику, а не по
строкам: у таблицы на 300 колонок 500 строк — это десятки мегабайт по сети.
Длинные значения обрезаются **на стороне БД**.

**У NER свой бюджет** — 50 значений на колонку вместо 500. Модель на порядок
медленнее регулярных выражений, а ей достаточно факта присутствия.

Следствие: **редкие** ПДн — одна строка на миллион — выборка может не
увидеть. Лечится точечно, а не глобальным увеличением лимита:

```bash
pii-scan --limit 20000 --only prod-mysql --details
```

### Категории

По умолчанию ищутся **все** категории. Сузить набор можно в конфиге:

```yaml
scan:
  detectors: [names]
```

или ключом при запуске:

```bash
pii-scan --detectors names,contacts
```

| Категория | Что входит |
|---|---|
| `names` | ФИО целиком, отдельные части имени, ФИО в свободном тексте (NER) |
| `contacts` | почта, телефон, адрес, почтовый индекс, населённые пункты в тексте |
| `documents` | СНИЛС, ИНН, полис ОМС, паспорт, загранпаспорт, ВУ, свидетельство о рождении |
| `finance` | номер банковской карты, банковский счёт |
| `birth` | дата и место рождения |

Полный перечень, включая группы, которых здесь нет, и все правила поштучно,
выдаёт `pii-scan --list-detectors`. Вместо группы можно указать отдельное
правило — `snils`, `bank_card`.

| | |
|---|---|
| **Латиница** | названия задаются латиницей: в конфигах и командной строке кириллица ломается на кодировках. Русские написания (`фио`, `контакты`) принимаются как псевдонимы |
| **В отчётах** | печатаются **русские** названия: «Искали: ФИО, контакты» — документ читает проверяющий, а не тот, кто правил конфиг |
| **Отключаются правила, а не колонки** | значения всех полей читаются и проверяются как обычно. При `--detectors names` колонка с почтой по-прежнему читается, но правило «адрес электронной почты» к ней не применяется |
| **Что реально ускоряется** | только NER: если распознавание по свободному тексту не входит в выбранные категории, модель не загружается |
| **Пометка в отчёте** | в шапке появляется строка «Искали: ФИО» и предупреждение, что отчёт нельзя считать полным обследованием |

### Уверенность и вердикты

```
доля  = совпавших значений / содержательных значений колонки
score = min(1, доля / 0.5) × вес правила
        + 0.35, если сработало имя поля или комментарий к нему
```

Полный вид со всеми ветвями — [«Формула уверенности»](#формула-уверенности)
в справочнике.

| Оценка | Вердикт | Куда попадает |
|---|---|---|
| **≥ 70 %** | ПДн | лёгкий отчёт, реестр |
| **35–70 %** | требует ручной проверки | подробный отчёт, лист «Требует проверки» |
| **< 35 %** | не обнаружено | только в полную опись, как «слабый признак» |

Три свойства формулы, которые объясняют её поведение:

**Половина колонки — уже полная уверенность** (деление на 0.5). Выше
половины уточнять нечего: колонка, где ПДн в каждом втором значении, носитель
персональных данных ничуть не меньше, чем колонка, где они в каждом.

| Совпало из 500 | Оценка | Вердикт |
|---|---|---|
| 1 | 0 % | не обнаружено |
| 25 | 10 % | не обнаружено |
| 50 | 20 % | не обнаружено |
| 100 | 40 % | требует проверки |
| 250 | **100 %** | **ПДн** |
| 485 | **100 %** | **ПДн** |

**Заглушки не входят в знаменатель.** `-`, `н/д`, `не указан`, `NULL`,
`нет данных` — записанное отсутствие значения, а не другое значение. Колонка
из 319 телефонов и 360 прочерков даёт 100 %, а не 47 %. Неоднозначные `0`,
`нет`, `x` заглушками не считаются: ошибка в эту сторону завышала бы долю.
Знаменатель не опускается ниже десятой части прочитанного — иначе колонка из
пятисот «н/д» и одного телефона давала бы стопроцентную уверенность.

**Потолок задаёт вес правила, и насыщение его не поднимает.** Колонка
сплошных десятизначных чисел совпадает с форматом паспорта на все 100 %, но
контрольной суммы у этого правила нет: вес 0.45, и выше «требует проверки»
такая колонка не поднимется ни при какой доле. Это и защищает от ложных
срабатываний на технических идентификаторах. См. [Веса правил](#веса-правил).

#### «Совпало 0, а уверенность 35 %»

Имя совпало, значения не подтвердили — ровно 0,35, впритык к порогу «требует
проверки». Порог не понижен намеренно: такое чаще означает **разрыв в
правилах**, а не ложное срабатывание.

```
crm.clients.passport_seria  char(4)  8148, 4881, 4767 …   0/500  35%
crm.clients.passport_nomer  char(6)  377139, 222143 …     0/500  35%
```

Это настоящие паспортные данные. Совпадений нет потому, что правило ищет
серию и номер вместе, а схема разнесла их по двум колонкам: четыре цифры сами
по себе — просто четыре цифры. Так же ведёт себя `last_name` с латиницей:
правила ФИО работают по кириллице, «Smith» им не опознать.

Поэтому разбор **разделён по основанию**, а не по оценке — работа разная:

```
  Требуют проверки:        0 табл. / 9 полей
    подтверждено значениями: 7      ← смотреть содержимое глазами
    только по имени поля:    2      ← спрашивать у разработчиков, что внутри
```

Счёт идёт по **полям, а не по таблицам**: `passport_seria` лежит в таблице,
где ФИО уже нашлись, поэтому таблица давно числится «с ПДн» — но поле
разбирать всё равно придётся.

Обратная сторона полноты: колонка городов (Ростов, Псков, Киров неотличимы
от фамилий по значению) выйдет в «требует проверки». Для 152-ФЗ пропущенное
поле дороже лишней строки на проверку.

## Работа на проде

### Что делается для безопасности

* `COUNT(*)` не выполняется никогда — размер берётся из `information_schema` /
  `system.tables` / `pg_class.reltuples`;
* одна выборка на таблицу, а не по запросу на колонку;
* значения обрезаются **на стороне сервера** (`LEFT(CAST(...))`,
  `substring(toString(...))`) — по сети не едут мегабайтные тексты;
* жёсткий таймаут запроса и ограничение `max_threads`;
* никаких `ORDER BY RAND()` — только `LIMIT`;
* `Distributed`, `Merge` и представления в ClickHouse пропускаются: иначе одни
  и те же данные попадут в отчёт по нескольку раз;
* примеры значений в отчёт не выносятся, пока их явно не попросят.

### Ограничение нагрузки

Главная опасность для работающей базы — не процессор, а вымывание буферного
пула: сканер читает страницы каждой таблицы, и они вытесняют горячие данные
приложения.

```yaml
throttle:
  pause_ms: 200               # пауза между запросами
  max_queries_per_minute: 60  # либо потолок темпа
  max_duration_min: 30        # бюджет времени: по исчерпании прогон
                              # завершается корректно и сохраняет найденное
```

Те же параметры доступны ключами `--pause-ms`, `--max-qpm`, `--max-minutes`.

Дополнительно у каждого источника есть проброс настроек сессии — точное
управление средствами самой СУБД:

```yaml
sources:
  - name: prod-clickhouse
    type: clickhouse
    settings:
      max_bytes_to_read: 100000000        # жёсткий потолок чтения на запрос
      max_execution_speed_bytes: 20000000 # родное ограничение скорости, байт/с
      max_memory_usage: 1000000000
      priority: 10                        # фоновый приоритет запросов

  - name: prod-mysql
    type: mysql
    settings:
      max_execution_time: 5000            # мс
```

**Рекомендуемый порядок на проде:**

1. `--dry-run` — только схема, ни одной строки данных. Уже покажет поля,
   названные явно.
2. Полный прогон на **реплике**, если она есть, — там вымывание кэша никому
   не мешает.
3. Реплики нет — ночное окно, `--pause-ms 200 --max-minutes 60`,
   `--limit 200`. Прогон, оборванный по бюджету, не теряет результат.

### Большие базы и сложные схемы

Стоимость прогона определяется не гигабайтами, а числом объектов: 50 ГБ в
двадцати таблицах — это двадцать запросов, те же 50 ГБ в пяти тысячах
партиций — пять тысяч.

| Механизм | Как работает |
|---|---|
| **Однотипные таблицы — по образцу** | `orders_2016_01 … orders_2025_12`, `sessions_shard_00 … shard_63` группируются по имени с точностью до чисел **и** по совпадению набора полей. Читается пара самых крупных представителей, остальным переносится результат с пометкой «по образцу». Отключается `--no-grouping` |
| **Вероятное — первым** | таблицы, где имена полей намекают на ПДн, идут в начале очереди. Если прогон оборвётся по времени, в отчёт успеет попасть главное |
| **Широкие таблицы — мельче** | выборка ограничивается трафиком (`max_bytes_per_table`), а не числом строк |

**Замеры на стенде.** 285 таблиц, 1277 колонок в MySQL (120 помесячных
партиций, 64 шарда, 100 справочников, таблица на 120 колонок) плюс ClickHouse:

| Режим | Обследовано таблиц | Время |
|---|---|---|
| Без группировки | 290 из 290 | 18.8 с |
| С группировкой (по умолчанию) | **12 из 290**, остальные по образцу | 10.5 с |
| Пауза 200 мс между запросами | 12 | 13.2 с |
| Бюджет 1 мин, пауза 300 мс, без группировки | 188 из 290, остановлен по времени | 67 с |

Во всех четырёх режимах найден один и тот же набор таблиц с ПДн — включая
прогон, оборванный по бюджету: приоритизация вывела нужное вперёд, а
пропущенными оказались справочники без персональных данных.

### Ограничения метода

* **Работа по выборке.** По умолчанию 500 строк с начала и с конца таблицы,
  см. [Что читается из таблицы](#что-читается-из-таблицы). ПДн, встречающиеся
  в единичных строках, сканер может не увидеть — увеличивайте `--limit` для
  подозрительных таблиц точечно.
* **Нераспознаваемые значения.** Диагнозы, национальность и подобное словами
  распознать нечем: «гипертония» для regex неотличима от любого другого
  слова. Такое поле находится по имени или комментарию, а названное
  `field_23` и не прокомментированное — только если в нём лежат коды МКБ-10
  (`I10`, `E11.9`) или что-то ещё распознаваемое.
* **Ложные срабатывания контрольных сумм.** Около 1/11 случайных
  десятизначных чисел формально проходят проверку ИНН. Гасится долей
  совпадений по колонке: одно валидное значение из трёхсот находкой не
  становится.
* **Повреждённые кодировки.** Кириллица в MySQL, записанная через соединение
  с неверной кодировкой (`Ð“Ð¾Ð»ÑƒÐ±ÐµÐ²` вместо `Голубев`), распознаётся и
  восстанавливается для анализа — иначе в legacy-базе сканер молча пропустил
  бы все ФИО и адреса. В отчёт добавляется предупреждение: саму базу это не
  чинит.
* **Юридический статус.** Результат — основание для проверки, а не
  квалификация. Решение об отнесении сведений к персональным данным принимает
  оператор.

## Справочник

### Формула уверенности

Оценка считается **для каждого правила отдельно**, уверенность колонки — это
максимум по правилам. Пояснения к шагам — в разделе
[Уверенность и вердикты](#уверенность-и-вердикты).

```
Обозначения для правила d в колонке c:

  m   — значений выборки, совпавших с правилом d
  N   — содержательных значений в колонке (прочитано минус пустые и заглушки)
  S   — прочитано значений всего (включая заглушки)
  E   — просмотрено правилом, если у него свой бюджет (только NER)
  w   — вес правила d (0.30 … 1.00, таблица ниже)
  имя — правило совпало с именем колонки или комментарием к ней


1. Знаменатель               D = E,  если у правила свой бюджет (NER)
                             D = max(N, S / 10)  в остальных случаях

2. Доля                      r = m / D           (r = 0, если D = 0)

3. Базовая оценка
     свободный текст (NER)   s = w,              если m >= 3 или r >= 0.05
                             s = r × w           иначе
     остальные правила       s = min(1, r / 0.5) × w

4. Бонус за имя              s = s + 0.35        если имя

5. Правила, где имя решает   s = max(s, 0.75)    если имя и в колонке есть данные
   (health, relatives,       s = max(s, 0.50)    если имя и колонка пуста
    birth_place, birth_certificate, special_other)

6. Пустая колонка            s = max(s, 0.50)    если имя, N = 0 и это не --dry-run

7. Оценка правила            score_d = min(1, s), округление до 3 знаков


Уверенность колонки          score = max(score_d по всем сработавшим правилам)

Вердикт                      score >= 0.70  ->  ПДн
                             score >= 0.35  ->  требует проверки
                             иначе          ->  не обнаружено
```

Шаг 4 не отменяет шага 3: имя и значения складываются. Шаги 5 и 6 не
складываются ни с чем — это нижние границы, а не слагаемые.

Коэффициент из шага 4 настраивается (`name_boost`); остальные числа —
константы в `pii_scan/model.py`.

**Разбор на примере.** Колонка `number_b`: прочитано 679 значений, из них 280
заглушек (`-`, `н/д`, `не указан`, `NULL`), 319 распознаны как телефоны, имя
колонки ни с чем не совпало.

```
N = 679 - 280 = 399          содержательных значений
D = max(399, 679/10 = 67)    = 399
r = 319 / 399                = 0.799
s = min(1, 0.799/0.5) × 1.00 = 1.00     доля выше половины — потолок
имя не совпало               бонуса нет
score                        = 1.00  ->  ПДн
```

### Веса правил

Вес — потолок, которого правило достигает при доле от половины и выше. Он
отражает, насколько само по себе совпадение доказательно.

| Вес | Правила | Почему столько |
|---|---|---|
| `1.00` | СНИЛС, номер банковской карты, адрес почты, телефон, ФИО | Контрольная сумма или своя однозначная форма — случайным такое совпадение почти не бывает |
| `0.90` | ИНН, ФИО в свободном тексте (NER) | Контроль есть, но десятизначный ИНН случайно проходит его в одном случае из одиннадцати |
| `0.85` | полис ОМС | Контроль по алгоритму Луна: случайно проходит один из десяти |
| `0.60` | адрес, свидетельство о рождении | Форма узнаваемая, но не строгая |
| `0.50` | дата рождения, отдельная часть имени | Дата бывает любой, одиночное слово с заглавной — тем более |
| `0.45` | паспорт РФ, загранпаспорт, ВУ, банковский счёт, здоровье (коды МКБ-10), топоним в тексте (NER) | Только формат, контрольной суммы нет. Потолок ниже порога ПДн: колонка сплошных десятизначных чисел останется «требует проверки» при любой доле |
| `0.30` | почтовый индекс | Шестизначных чисел в базах слишком много |

У правил без распознавания по значению (место рождения, спецкатегории,
родственники) вес формально равен `1.00`, но в расчёте не участвует: их вывод
целиком делают шаги 5 и 6.

### Параметры конфига

Конфиг состоит из трёх блоков: `scan` — что и как обследовать, `throttle` —
сколько нагрузки создавать, `sources` — к чему подключаться. Обязателен
только `sources`; всё остальное имеет разумные значения по умолчанию.

Почти каждый параметр `scan` дублируется ключом запуска, и **ключ имеет
приоритет над конфигом**: постоянные настройки живут в файле, разовые
задаются в командной строке.

#### `scan` — объём выборки

| Параметр | Умолчание | На что влияет |
|---|---|---|
| `sample_limit` | `500` | Сколько строк читается из каждой таблицы. Больше — выше шанс поймать редкие ПДн и выше нагрузка. Ключ `--limit`. |
| `sample_strategy` | `head_tail` | Откуда берутся строки: `head` — начало таблицы, `tail` — конец, `head_tail` — пополам с обоих концов. Поле, которое начали заполнять недавно, в старых строках пусто, поэтому чтение одной «головы» объявит его чистым. Требует первичного ключа или ключа сортировки; без него читается только начало. Ключ `--strategy`. |
| `max_value_len` | `512` | До скольких символов обрезается значение **на стороне БД**. Защищает от выкачивания blob-полей целиком. Слишком малое значение обрезает длинные ФИО и адреса. |

#### `scan` — что искать

| Параметр | Умолчание | На что влияет |
|---|---|---|
| `detectors` | `[]` (все) | Какие категории ПДн искать: `names`, `contacts`, `documents`, `finance`, `birth` и другие, либо отдельные правила вроде `snils`. Отключаются **правила, а не колонки** — значения всех полей читаются и проверяются как обычно. Перечень выдаёт `--list-detectors`. Ключ `--detectors`. |
| `ner` | `true` | Распознавание ФИО и топонимов в свободном тексте. Ловит ПДн в комментариях и примечаниях, куда они попадают незаметно. Заметно замедляет прогон и требует полного образа; в slim-образе выключается с записью в лог. Ключ `--no-ner`. |
| `ner_values_per_column` | `50` | Сколько значений колонки отдаётся NER. Квота гораздо меньше `sample_limit`: инференс на два порядка дороже регулярного выражения, а модели достаточно факта присутствия. Значения выбираются равномерно по всей выборке. |
| `scan_json` | `true` | Разбирать ли JSON внутри значений. Каждый ключ становится виртуальной колонкой вида `payload::$.client.phone`. |
| `max_json_paths` | `200` | Потолок виртуальных колонок на одну JSON-колонку. Защита от документов с сотнями разных ключей. |
| `dry_run` | `false` | Только инвентаризация схемы: имена и комментарии колонок, **ни одной прочитанной строки данных**. С этого начинают на незнакомом проде. Ключ `--dry-run`. |

#### `scan` — оценка и отчёты

| Параметр | Умолчание | На что влияет |
|---|---|---|
| `name_boost` | `0.35` | Вклад совпадения по имени колонки в уверенность. Понижение убирает из отчёта поля, которые держатся на одном названии, но заодно снимает уверенность с подтверждённых находок, а правила, где имя решает само, ему не подчиняются. Для упрощённого отчёта берите `confirmed_only`. Ключ `--name-boost`. |
| `confirmed_only` | `false` | Оставить в отчётах только находки, подтверждённые содержимым. Число исключённых объявляется предупреждением. Ключ `--confirmed-only`. |
| `full_inventory` | `false` | Добавить в отчёты **все** поля всех обследованных таблиц, включая те, где ничего не найдено — доказательство охвата. Заметно увеличивает объём отчётов. Ключ `--full-inventory`. |
| `examples_per_hit` | `0` | Сколько замаскированных примеров значений показывать. Ноль — не показывать вовсе: даже маска оставляет длину, формат и первые символы. Ключ `--examples [N]`. |
| `show_values` | `false` | Снять маскировку с примеров. **Отчёт становится полноценным носителем ПДн** со всеми требованиями к его хранению. Включает примеры, даже если `examples_per_hit` равен нулю. Ключ `--show-values`. |
| `progress` | `auto` | Индикатор выполнения: `auto` — только когда вывод идёт в терминал, `on` — всегда, `off` — никогда. Ключ `--progress`. |

#### `scan` — нагрузка и масштаб

| Параметр | Умолчание | На что влияет |
|---|---|---|
| `query_timeout` | `15` | Секунд на запрос. Ограничение выставляется **на стороне сервера** (`max_execution_time` в MySQL и ClickHouse, `statement_timeout` в PostgreSQL), поэтому зависший запрос убивает база, а не клиент. |
| `max_columns_per_query` | `60` | Сколько колонок читается одним запросом. Таблица на 300 колонок разбивается на пять запросов вместо одного гигантского. |
| `max_bytes_per_table` | `2000000` | Потолок трафика на таблицу, байт. У широкой таблицы сканер сам возьмёт меньше строк, чем `sample_limit`. |
| `max_threads` | `2` | Только ClickHouse: сколько потоков разрешено запросу. Прямое ограничение нагрузки на кластер. |
| `group_similar_tables` | `true` | Обследовать однотипные таблицы по образцу. На схеме из тысяч партиций это разница между минутами и часами. Ключ `--no-grouping`. |
| `group_min_size` | `4` | С какого размера группы включается наследование. Ниже порога дешевле прочитать все таблицы. |
| `group_samples` | `2` | Сколько представителей группы обследуется. Больше — надёжнее (партиции бывают неоднородны), дороже по времени. |
| `allow_rw` | `false` | Разрешить работу под учётной записью с правами на запись. По умолчанию такой запуск блокируется **до** сканирования. Ключ `--allow-rw`. |

#### `throttle` — ограничение нагрузки

По умолчанию не ограничивает ничего.

| Параметр | Умолчание | На что влияет |
|---|---|---|
| `pause_ms` | `0` | Пауза между запросами, мс. Главный регулятор: `200` растягивает прогон, но размазывает нагрузку так, что база её почти не замечает. Ключ `--pause-ms`. |
| `max_queries_per_minute` | `0` (без ограничения) | Потолок темпа запросов. Полезен, когда важна не пауза, а частота — например при общем лимите на реплику. Ключ `--max-qpm`. |
| `max_duration_min` | `0` (без ограничения) | Бюджет времени, минут. По исчерпании прогон **корректно завершается и сохраняет найденное**, а не обрывается. Ключ `--max-minutes`. |

#### `sources` — подключения

Список; каждый элемент — одна база. Обязательны `name`, `type`, `host`,
`user`; `port` подставляется по типу, если не задан.

| Параметр | Умолчание | На что влияет |
|---|---|---|
| `name` | — | Имя источника в отчётах и в ключе `--only`. |
| `type` | — | `mysql`, `postgres` или `clickhouse`. Определяет адаптер: как получить список таблиц, комментарии, оценку числа строк и права учётной записи. |
| `host` | — | Адрес сервера. Из контейнера `localhost` — это сам контейнер; для базы на хосте нужен `host.docker.internal` или адрес хоста. |
| `port` | по типу | `3306` для MySQL, `5432` для PostgreSQL, `8123` для ClickHouse. Для ClickHouse порт заодно **выбирает драйвер**: `8123`/`8443` — HTTP, `9000`/`9440` — нативный протокол. |
| `user` | — | Учётная запись. Нужен только `SELECT`; права на запись блокируют запуск. |
| `password` | `""` | Пароль. В файл не пишется: `${MYSQL_PWD}` подставляется из окружения, поддерживается и `${VAR:-значение}`. Отсутствующая переменная — ошибка запуска, а не пустой пароль. |
| `secure` | `false` | TLS: HTTPS для ClickHouse, SSL-соединение для MySQL, `sslmode=verify-full` для PostgreSQL. |
| `ssl_ca` | `""` | Путь к корневому сертификату **внутри контейнера** — файл нужно смонтировать, например в `/config/ca.pem`. |
| `ssl_verify` | `true` | Проверять ли сертификат сервера. Отключение оставляет шифрование, но снимает защиту от подмены. |
| `databases` | `[]` (все) | Какие базы обследовать. Точные имена, не regex. Системные исключаются всегда. |
| `exclude_databases` | `[]` | Что дополнительно пропустить. К списку автоматически добавляются системные базы: `mysql`, `information_schema`, `performance_schema`, `sys` для MySQL; `template0`, `template1` для PostgreSQL; `system`, `information_schema` для ClickHouse. |
| `include_tables` | `[]` (все) | Регулярные выражения. Если список непуст, обследуются **только** совпавшие таблицы. Проверяется и полное имя `база.таблица`, и короткое. |
| `exclude_tables` | `[]` | Регулярные выражения для пропуска. Имеют приоритет над `include_tables`. Типовое применение — `'_archive$'`, `'^tmp_'`. |
| `skip_views` | `true` | Пропускать представления. Данные в них те же, что в таблицах, и без пропуска они попадут в отчёт дважды. |
| `skip_engines` | `[Distributed, Merge, Null, View, MaterializedView]` | Только ClickHouse: движки, которые не сканируются. `Distributed` и `Merge` читают те же данные из других таблиц. Пустой список включает их обратно. |
| `settings` | `{}` | Переменные сессии, выставляемые на соединении: `max_execution_time` в MySQL, `work_mem` в PostgreSQL, `max_bytes_to_read` и `priority` в ClickHouse. Способ применить родные ограничители СУБД поверх настроек сканера. |

### Ключи запуска

```
--config PATH             путь к конфигу (в контейнере /config/config.yml)
--out DIR                 каталог отчётов (по умолчанию /out)
--formats СПИСОК          summary,detailed,json,xlsx или all
--dry-run                 только схема, значения не читаются
--limit N                 строк выборки на таблицу
--strategy head|tail|head_tail   откуда брать выборку
--only ИМЯ                только указанный источник (можно повторять)
--no-ner                  отключить NER по свободному тексту
--no-json                 не разбирать JSON внутри значений
--allow-rw                разрешить учётную запись с правами на запись
--details / -d            разбивка по полям прямо в консоли
--full-inventory          в отчёты все поля всех таблиц, включая чистые
--detectors СПИСОК        какие категории искать: names, contacts, …
--list-detectors          показать доступные категории и правила
--confirmed-only          упрощённый отчёт: только находки, подтверждённые
                          содержимым (число исключённых объявляется)
--name-boost N            вклад совпадения по имени колонки (по умолчанию 0.35)
--examples [N]            показать N замаскированных примеров (без числа — 3;
                          по умолчанию примеры не показываются)
--show-values             не маскировать примеры (отчёт станет носителем ПДн)
--progress auto|on|off    индикатор выполнения
-q / -v                   тише / подробнее

Ограничение нагрузки:
--pause-ms МС             пауза между запросами к БД
--max-qpm N               не больше N запросов в минуту
--max-minutes МИН         бюджет времени на прогон
--no-grouping             не наследовать результат на однотипные таблицы
```

Полный список — `pii-scan --help`.

### Коды возврата

| Код | Значение |
|---|---|
| `0` | успех |
| `1` | были ошибки при сканировании |
| `2` | ошибка конфигурации |
| `3` | запуск заблокирован из-за прав на запись |

## Разработка

### Тестовый стенд

Генератор синтетических данных: вымышленные ФИО и адреса, валидные по
контрольным суммам СНИЛС/ИНН/ОМС/карты, ПДн внутри JSON и в свободном тексте,
плюс намеренные ловушки на ложные срабатывания (технические коды, журналы,
метрики, настройки).

```bash
cd testdata && python generate.py . && docker compose -f docker-compose.test.yml up -d
```

Поднимутся MySQL с базой `crm`, PostgreSQL с базой `shop` (схемы `crm` и
`ops`) и ClickHouse с базой `analytics` в сети `pii-test-net`, вместе с
учётными записями `pii_reader` (только чтение) и `app_rw` / `etl_writer` (с
правами на запись — для проверки блокировки).

Сканер запускается в той же сети:

```bash
docker run --rm --network pii-test-net --user "$(id -u):$(id -g)" -v "$PWD/config:/config:ro" -v "$PWD/out:/out" -e MYSQL_PWD='ReadOnly_2026!' -e CH_PWD='ReadOnly_2026!' pii-scan:full --config /config/config.yml
```

### Сборка и тесты

```bash
python -m venv .venv && . .venv/bin/activate
pip install -r requirements.txt -r requirements-nlp.txt pytest
python -m pytest tests -q
```

### Устройство

| Модуль | Ответственность |
|---|---|
| `pii_scan/detectors.py` | правила распознавания — единственное место, где живёт знание о ПДн. Ввода-вывода не делает, тестируется без БД |
| `pii_scan/model.py` | находки и скоринг |
| `pii_scan/scanner.py` | оркестрация: последовательность действий, не знает ни SQL, ни правил |

| `pii_scan/report/` | вывод: консоль, markdown, XLSX, JSON |
