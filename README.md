# pii-scan

Поиск персональных данных (152-ФЗ) в **MySQL**, **PostgreSQL** и
**ClickHouse**. Отвечает на один вопрос: в каких таблицах и полях лежат ПДн,
каких категорий и насколько можно доверять выводу.

Утилита ничего не пишет в обследуемые БД, никуда не передаёт данные по сети и
не маскирует поля — только находит и документирует.

| СУБД | Проверено вживую |
|---|---|
| MySQL / MariaDB | MySQL 8.4 |
| PostgreSQL | PostgreSQL 16, несколько схем в одной базе |
| ClickHouse | ClickHouse 24.8, HTTP и нативный протокол |

| Файл | Назначение |
|---|---|
| `summary.md` | Лёгкий отчёт: только уверенные находки, строка на таблицу. Для владельца системы и руководителя. |
| `detailed.md` | Подробный отчёт: все находки, включая пограничные, с основанием вывода. Примеры значений добавляются ключом `--examples`. |

## Подготовка

Что нужно сделать до первого запуска: выдать учётную запись и убедиться, что сканер до базы дотянется.

### Учётные записи в БД

Сканеру нужен **только SELECT**. Наличие прав на запись блокирует запуск —
это защита от прогона под административной учёткой на проде.

#### MySQL

```sql
CREATE USER 'pii_reader'@'10.0.0.%' IDENTIFIED BY 'СЛОЖНЫЙ_ПАРОЛЬ';
GRANT SELECT ON *.* TO 'pii_reader'@'10.0.0.%';
```

Используются: `information_schema.TABLES` и `information_schema.COLUMNS` для
структуры, `SHOW GRANTS FOR CURRENT_USER()` для проверки режима только чтения,
`SELECT` для выборки значений. Отдельные привилегии на `information_schema`
выдавать не нужно, но помните: MySQL показывает там только те объекты, на
которые у пользователя есть хоть какие-то права. Если выдать SELECT лишь на
одну базу, остальные сканер попросту не увидит — это удобный способ ограничить
охват. `PROCESS`, `SUPER`, `RELOAD` не нужны.

Чтобы обследовать не весь сервер:

```sql
GRANT SELECT ON crm.* TO 'pii_reader'@'10.0.0.%';
GRANT SELECT ON billing.* TO 'pii_reader'@'10.0.0.%';
```

#### PostgreSQL

```sql
CREATE ROLE pii_reader LOGIN PASSWORD 'СЛОЖНЫЙ_ПАРОЛЬ';
GRANT CONNECT ON DATABASE имя_базы TO pii_reader;
GRANT USAGE ON SCHEMA public TO pii_reader;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO pii_reader;
ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT SELECT ON TABLES TO pii_reader;
```

Права выдаются **в каждой обследуемой базе отдельно**: в PostgreSQL нет
межбазовых запросов, поэтому сканер открывает своё подключение на каждую базу.
Если `databases` в конфиге не задан, он перечислит все базы, к которым
разрешено подключаться, и обойдёт их по очереди.

Используются `pg_database`, `pg_class`, `pg_namespace`, `pg_attribute`,
`pg_index` для структуры, `col_description()` для комментариев к полям,
`information_schema.role_table_grants` и `pg_roles` для проверки прав.
Размер таблиц берётся из `pg_class.reltuples` — оценки планировщика,
`COUNT(*)` не выполняется. Права суперпользователя (`SUPERUSER`, `CREATEDB`,
`CREATEROLE`) считаются правами на запись.

Имена таблиц трёхуровневые: в отчёте они выглядят как `база.схема.таблица`,
иначе `public.clients` и `billing.clients` слились бы в одну строку.

#### ClickHouse

```sql
CREATE USER pii_reader IDENTIFIED WITH sha256_password BY 'СЛОЖНЫЙ_ПАРОЛЬ'
    SETTINGS readonly = 2;
GRANT SELECT ON *.* TO pii_reader;
```

`readonly = 2`, а не `1`: сканер выставляет для своих запросов
`max_execution_time` и `max_threads`, чтобы не нагружать сервер, — при
`readonly = 1` сервер запретит менять настройки и запросы упадут.

Используются `system.tables` и `system.columns` (видны объекты, к которым есть
доступ), `system.settings` для проверки режима readonly, `SHOW GRANTS` и
`SELECT`. Права `ADMIN`, `SYSTEM`, `INTROSPECTION` не нужны.

#### Если учётка с правами на запись

Запуск блокируется с кодом возврата `3` и перечнем найденных привилегий.
Обойти можно флагом `--allow-rw` — в отчёте и в консоли останется отметка, что
источник сканировался не в режиме только чтения.

### Подключение по сети

Сканер подключается к СУБД по обычному сетевому соединению — БД могут стоять
на других серверах, локально ничего разворачивать не нужно.

| СУБД | Порт по умолчанию | Протокол | Драйвер |
|---|---|---|---|
| MySQL / MariaDB | 3306 | родной протокол MySQL | PyMySQL (запасной — mysql-connector) |
| PostgreSQL | 5432 | родной протокол | psycopg 3 (запасной — psycopg2) |
| ClickHouse | 8123 (HTTPS — 8443) | HTTP | clickhouse-connect |
| ClickHouse | 9000 (TLS — 9440) | нативный | clickhouse-driver |

Драйвер ClickHouse выбирается **по указанному порту**, оба пакета есть в
образе. Если в конфиге стоит 9000, а сканер идёт по HTTP — значит, образ
старый, пересоберите (`git pull && ./install.sh`).

TLS включается флагом `secure: true`; при необходимости укажите корневой
сертификат `ssl_ca` (путь **внутри контейнера**, положите файл в `config/`) и
`ssl_verify: false`, если сертификат самоподписанный и проверять его не нужно.

Что важно в Docker:

* **БД на другом сервере** — работает как есть, ничего настраивать не надо.
* **БД на том же хосте, слушает 127.0.0.1** — из контейнера этот адрес указывает
  на сам контейнер. Раскомментируйте `network_mode: host` в
  `docker-compose.yml` либо используйте `host.docker.internal` вместе с
  `extra_hosts: ["host.docker.internal:host-gateway"]`.
* **Доступ по имени хоста из внутренней DNS** — если контейнер её не видит,
  пропишите адреса через `extra_hosts` в compose-файле.

Наружу, в интернет, утилита не ходит: HTTP-клиента в коде нет, модели NER
загружаются с диска. Контейнеру достаточно доступа к портам обследуемых СУБД.

## Установка

Способа два, и это **альтернативы**, а не шаги подряд. Результат одинаковый:
собранный образ, каталоги `config/` и `out/`, готовые к правке `config.yml`
и `.env`. Разница в том, кто делает шаги — скрипт или вы.

| Способ | Когда выбирать |
|---|---|
| [Установщик](#способ-1-установщик) | по умолчанию: сам проверит окружение, соберёт образ и поставит команду `pii-scan` |
| [Вручную](#способ-2-вручную) | нельзя ставить команду в систему, свой процесс сборки, либо образ приезжает готовым файлом |

Из общего — только клонирование репозитория:

```bash
git clone https://github.com/vehpbkrby/pii-scan.git && cd pii-scan
```

Дальше выбирайте один из двух способов. Ниже них — [что внутри
образа](#об-образе) и [частные случаи](#частные-случаи-установки): корпоративный
TLS-инспектор, сервер без интернета, недоступный docker.

### Способ 1: установщик

```bash
./install.sh
```

Скрипт проверит docker и место на диске, создаст `config/` и `out/`, положит
`config.yml` и `.env` из примеров (`.env` с правами 600), соберёт образ и
поставит команду `pii-scan` — обёртку над `docker run` с нужными томами,
`--user` и выделением терминала под индикатор выполнения.

| Ключ | Что делает |
|---|---|
| `./install.sh` | образ с NER (276 МБ) |
| `./install.sh --slim` | образ без NER (164 МБ) — для закрытого контура |
| `./install.sh --systemd weekly` | плюс регулярный прогон по расписанию systemd |
| `./install.sh --uninstall` | убрать команду и юниты (образ и отчёты остаются) |

Команда ставится в `/usr/local/bin`, если есть root или беспарольный sudo,
иначе в `~/.local/bin`.

Запускайте установщик **от своего пользователя**, а не из-под `sudo su`:
сканировать вы будете от себя, и созданный root-ом каталог `out/` окажется
недоступен для записи. Если всё же ставили от root, установщик сам вернёт
`config/`, `out/` и `.env` владельцу каталога проекта.

### Способ 2: вручную

То же самое тремя командами. Команда `pii-scan` при этом не появится —
запускать придётся через `docker run` или `docker compose`, см.
[Запуск без установщика](#запуск-без-установщика).

**1. Каталоги и заготовки конфигов:**

```bash
mkdir -p config out && cp config.example.yml config/config.yml
```

**2. Файл с паролями** (права 600 выставьте сами — установщик делает это за
вас):

```bash
cp .env.example .env && chmod 600 .env
```

**3. Образ:**

```bash
docker build --build-arg WITH_NLP=1 -t pii-scan:full .
```

Дальше — [Первый запуск](#первый-запуск-по-шагам), только вместо `pii-scan`
подставляйте команду `docker run` из раздела про запуск без установщика.

### Об образе

Раздел общий для обоих способов: установщик внутри вызывает тот же
`docker build`.

Образ собирается в двух вариантах — с распознаванием по свободному тексту
и без него:

```bash
docker build -t pii-scan:slim .                          # 164 МБ, только regex
docker build --build-arg WITH_NLP=1 -t pii-scan:full .   # 276 МБ, + NER
```

Размеры измерены на Ubuntu 25.10, Docker 28.2.

`docker compose` собирает вариант из переменной `WITH_NLP` в `.env` (по
умолчанию — с NER). Для закрытого контура удобнее `slim`: в нём нет моделей и
объяснять безопасникам лишние 500 МБ весов не придётся.

База образа — `python:3.10-slim`. Это не случайность: `natasha` тянет
`pymorphy2`, который использует `inspect.getargspec`, удалённый в Python 3.11.

Модели NER (`navec`, `slovnet`) упакованы внутрь пакета `natasha` и ставятся
на этапе сборки. **В рантайме доступ в интернет не нужен**: инференс идёт
локально на CPU, HTTP-клиента в коде нет. Контейнеру нужен доступ только к
портам обследуемых СУБД.

### Частные случаи установки

#### Если install.sh не видит docker

Две самые частые причины, обе неочевидные:

**Демон не запущен.** `systemctl enable docker` только прописывает автозапуск
при загрузке, но сам сервис не поднимает:

```bash
sudo systemctl start docker
```

**Группа выдана, но не применилась.** `usermod -aG docker` меняет базу групп,
однако уже запущенная сессия свой список групп не перечитывает — он выдаётся
при входе в систему. Поэтому в том же терминале доступа по-прежнему нет:

```bash
newgrp docker                 # применить в текущей сессии
sg docker -c ./install.sh     # либо сразу запустить установку
```

Либо выйти из системы и зайти заново. Проверить, что обе причины закрыты:

```bash
systemctl is-active docker && id -nG | tr ' ' '\n' | grep -x docker && docker info >/dev/null && echo ок
```

Установщик различает эти случаи и подсказывает нужную команду — если он
сообщает что-то другое, читайте его вывод, там конкретика.

#### Корпоративный TLS-инспектор

Если сборка падает так:

```
[SSL: CERTIFICATE_VERIFY_FAILED] certificate verify failed:
self-signed certificate in certificate chain
ERROR: No matching distribution found for wheel
```

значит, трафик разбирает корпоративный TLS-инспектор: он подменяет
сертификат pypi.org своим. Сам сервер этому корню доверяет, а контейнер при
сборке — ещё нет, у него собственное хранилище. Передайте связку сертификатов
хоста в сборку:

```bash
./install.sh --ca-cert /etc/ssl/certs/ca-certificates.crt
```

Установщик положит её в контекст сборки как `ca-cert.crt` (файл в
`.gitignore`), образ добавит сертификат в системное хранилище и укажет его
pip через `PIP_CERT` — **pip проверяет сертификаты по связке certifi, а не по
системному хранилищу**, поэтому одного `update-ca-certificates` мало.

Если PyPI закрыт полностью, а внутреннее зеркало есть:

```bash
./install.sh --pip-index https://nexus.corp/repository/pypi/simple --trusted-host nexus.corp
```

При сборке вручную это те же аргументы:

```bash
docker build --build-arg WITH_NLP=1 --build-arg PIP_INDEX_URL=... --build-arg PIP_TRUSTED_HOST=... -t pii-scan:full .
```

#### Сервер без доступа в интернет

Сборка образа — единственный шаг, которому нужен интернет (pip тянет
зависимости). В закрытом контуре соберите образ на машине с доступом и
перенесите файлом:

```bash
docker build --build-arg WITH_NLP=1 -t pii-scan:full .     # там, где есть интернет
docker save pii-scan:full | gzip > pii-scan-full.tar.gz
```

```bash
gunzip -c pii-scan-full.tar.gz | docker load               # на закрытом сервере
./install.sh --skip-build
```

## Запуск

Порядок один и тот же на любой СУБД: сухой прогон без чтения данных, затем
полный. Ниже — пошагово, типовые сценарии и что делать, когда что-то идёт не
так.

### Первый запуск, по шагам

**1. Впишите пароли** — в конфиге их быть не должно, только ссылки `${VAR}`:

```bash
$EDITOR .env
```

```
MYSQL_PWD=пароль_учётки_pii_reader
CH_PWD=пароль_учётки_pii_reader
```

**2. Укажите, что обследуем** — адреса, учётные записи, при необходимости
фильтры баз и таблиц:

```bash
$EDITOR config/config.yml
```

Минимально достаточно этого:

```yaml
sources:
  - name: prod-mysql
    type: mysql
    host: 10.0.0.10
    user: pii_reader
    password: ${MYSQL_PWD}
```

Список таблиц перечислять не нужно — сканер сам прочитает структуру.

**3. Сухой прогон.** Читается только схема: имена таблиц, полей и комментарии.
**Ни одна строка данных не читается**, нагрузки на базу практически нет.

```bash
pii-scan --dry-run
```

Так проверяется и связь, и права, и охват — и уже видны поля, названные
явно. На прод всегда заходите с этого.

**4. Полный прогон** — с чтением выборки значений:

```bash
pii-scan
```

**5. Заберите отчёты** из каталога `out/`:

```
out/summary.md      лёгкий отчёт: только уверенные находки
out/detailed.md     подробный: все находки с основанием и примерами
out/registry.xlsx   реестр с автофильтром
out/findings.json   полная выгрузка для скриптов
```

Имена файлов постоянные, каждый прогон их перезаписывает. Две оговорки:

* с `--formats xlsx` (или любым неполным списком) остальные файлы **не
  обновляются и не удаляются** — в каталоге останутся отчёты от прошлого
  прогона со старой датой. Сверяйтесь с датой изменения или чистите `out/`;
* чтобы сохранить историю, копируйте `out/` с датой в имени — сравнение
  `findings.json` между прогонами показывает, что появилось нового.

### Что видно во время работы

```
13:20:41 INFO    Конфиг: /config/config.yml | источников: 2 | режим: выборка значений
13:20:41 INFO    Источник 'prod-mysql': таблиц 286, к обследованию 12, по образцу 274
prod-mysql [████████░░░░░░░░░░░░░░░░] 59/286  21% · осталось ~4 с  big.orders_2020_11
```

По завершении в консоль выводится сводка: сколько таблиц с ПДн и сколько
требует ручной проверки.

### Индикатор выполнения

В терминале сканер рисует полосу с текущей таблицей, процентом и оценкой
оставшегося времени:

```
prod-mysql [████████░░░░░░░░░░░░░░░░] 59/286  21% · осталось ~4 с  big.orders_2020_11
```

Полоса появляется только когда вывод идёт в терминал. В cron, systemd или
`docker run` без `-t` вместо неё пишутся редкие отметки в журнал (каждые 5%),
чтобы не плодить тысячи строк. Управляется ключом
`--progress auto|on|off`.

Команда `pii-scan`, поставленная установщиком, сама добавляет `-t` при
запуске из терминала. Если запускаете `docker run` руками — не забудьте флаг,
иначе индикатора не будет.

### Что живёт между прогонами

Ничего. Постоянно работающей службы нет: контейнер создаётся в момент запуска
`pii-scan` и удаляется сразу после завершения сканирования — обёртка запускает
`docker run --rm`.

| | Что это | Когда существует | Что потребляет |
|---|---|---|---|
| **Образ** `pii-scan:full` | файл на диске | постоянно, после сборки | 276 МБ диска, больше ничего |
| **Контейнер** | запущенный процесс | только во время сканирования | CPU и память на время прогона |

Между прогонами не остаётся ни фоновых процессов, ни открытых портов, ни
соединений с БД. Проверить:

```bash
docker ps | grep pii-scan
```

Пусто — значит, ничего не выполняется. Если строка есть, прогон идёт прямо
сейчас (как его остановить — см. ниже).

Отсюда же заметная деталь: модели NER загружаются с диска при **каждом**
запуске, около полутора секунд, поэтому первая таблица обрабатывается дольше
остальных. Это плата за отсутствие постоянной службы — для инструмента,
который запускают раз в неделю, размен оправданный. Если NER не нужен,
`--no-ner` убирает и эту задержку.

Исключение одно: с `./install.sh --systemd weekly` контейнер запускает по
расписанию таймер systemd. Но и там между запусками не работает ничего —
висит только сам таймер.

### Типовые сценарии

| Задача | Команда |
|---|---|
| Первичная инвентаризация, не трогая данные | `pii-scan --dry-run` |
| Полное обследование | `pii-scan` |
| Только один источник | `pii-scan --only prod-mysql` |
| Точечно, с большой выборкой | `pii-scan --limit 20000 --only prod-mysql` |
| Ночной прогон с ограничением нагрузки | `pii-scan --pause-ms 200 --max-minutes 120` |
| Быстрая прикидка без NER | `pii-scan --limit 100 --no-ner` |
| Только реестр XLSX | `pii-scan --formats xlsx` |
| Разбивка по полям в консоли | `pii-scan --details` |
| Полная опись всех полей, включая чистые | `pii-scan --full-inventory --details` |
| С примерами значений (маскированными) | `pii-scan --details --examples` |
| Каждая таблица отдельно, без наследования | `pii-scan --no-grouping` |
| Свежие записи вместо старых | `pii-scan --strategy tail` |
| Искать только одну категорию | `pii-scan --detectors names` |
| Несколько категорий сразу | `pii-scan --detectors names,contacts` |
| Одно конкретное правило | `pii-scan --detectors snils` |
| Посмотреть доступные категории | `pii-scan --list-detectors` |
| Опись по одному источнику для разработчиков | `pii-scan --only prod-postgres --full-inventory --formats xlsx` |
| Обследовать конкретную базу PostgreSQL | `databases: [shop]` в конфиге источника |
| ClickHouse по нативному протоколу | `port: 9000` в конфиге источника |
| Ограничить темп запросов | `pii-scan --max-qpm 60` |
| Отдать отчёты в другой каталог | `pii-scan --out /srv/audit/2026-08` |

### Примеры запусков

**Знакомство с базой, без чтения данных.** С этого начинают на проде:
читается только схема, нагрузки почти нет.

```bash
pii-scan --dry-run --details
```

**Полное обследование с ограничением нагрузки.** Пауза между запросами и
бюджет времени: прогон не мешает работе базы и гарантированно закончится.

```bash
pii-scan --pause-ms 200 --max-minutes 120
```

**Только ФИО в одной базе.** Категории сужают набор правил, `--only`
ограничивает источник.

```bash
pii-scan --detectors names --only prod-mysql
```

**Что вообще можно указать в категориях:**

```bash
pii-scan --list-detectors
```

**Точечная проверка одной таблицы с большой выборкой.** Полезно, когда поле
заполнено редко и обычных 500 строк не хватает: временно сузьте охват в
конфиге через `include_tables` и поднимите лимит.

```bash
pii-scan --limit 20000 --only prod-postgres --details
```

**Полная опись для разработчиков.** Каждое поле каждой таблицы с вердиктом,
включая чистые:

```bash
pii-scan --full-inventory --details
```

**Быстрая прикидка на большой схеме.** Без NER и с малой выборкой — минуты
вместо часов, годится чтобы понять масштаб:

```bash
pii-scan --limit 100 --no-ner
```

**Свежие записи вместо старых.** По умолчанию выборка берётся с обоих концов
таблицы; если данные заведомо новые, можно читать только хвост:

```bash
pii-scan --strategy tail
```

**Только реестр XLSX**, без остальных отчётов:

```bash
pii-scan --formats xlsx
```

**Каждая таблица отдельно.** По умолчанию однотипные таблицы (шарды,
помесячные партиции) обследуются по образцу — этот ключ отключает наследование:

```bash
pii-scan --no-grouping
```

**Прогон в cron или systemd.** Индикатор выключен, в журнал идут редкие
отметки:

```bash
pii-scan --progress off --pause-ms 200 --max-minutes 120
```

**Несколько источников в одном прогоне** — перечисляются в конфиге, ключей не
требуется:

```yaml
sources:
  - name: prod-mysql
    type: mysql
    host: 10.0.0.10
    user: pii_reader
    password: ${MYSQL_PWD}

  - name: prod-postgres
    type: postgres
    host: 10.0.0.15
    user: pii_reader
    password: ${PG_PWD}
    databases: [shop]

  - name: prod-clickhouse
    type: clickhouse
    host: 10.0.0.20
    port: 9000
    user: pii_reader
    password: ${CH_PWD}
```

```bash
pii-scan
```

### Запуск без установщика

Через compose:

```bash
PII_UID=$(id -u) PII_GID=$(id -g) docker compose run --rm scanner --config /config/config.yml --dry-run
```

Через `docker run` напрямую:

```bash
docker run --rm -t --user "$(id -u):$(id -g)" --env-file .env -v "$PWD/config:/config:ro" -v "$PWD/out:/out" pii-scan:full --config /config/config.yml --dry-run
```

Что здесь важно:

* `--user "$(id -u):$(id -g)"` — внутри образа пользователь с uid 10001, без
  этого каталог `out/` окажется недоступен для записи. Права проверяются **до**
  сканирования, а не после: иначе многочасовой прогон терял бы результат на
  последнем шаге.
* `-t` — иначе не будет индикатора выполнения.
* `config` монтируется только на чтение, `out` — единственная точка записи.

### Если БД не видна из контейнера

| Ситуация | Что делать |
|---|---|
| БД на другом сервере | ничего, работает как есть |
| БД в docker-сети | `PII_NETWORK=имя_сети pii-scan` |
| БД на 127.0.0.1 того же хоста | `network_mode: host` в `docker-compose.yml` |
| Не резолвится имя хоста | `extra_hosts` в `docker-compose.yml` |

### Регулярные прогоны

```bash
./install.sh --systemd weekly
systemctl list-timers pii-scan.timer     # когда ближайший запуск
journalctl -u pii-scan.service           # как прошёл прошлый
```

Отчёты перезаписываются на каждом прогоне, поэтому при работе по расписанию
имеет смысл складывать их в архив. Добавьте в
`/etc/systemd/system/pii-scan.service` строку (знак процента в юнитах
удваивается):

```ini
ExecStartPost=/bin/sh -c 'cp -a out "archive/$(date +%%Y-%%m-%%d)"'
```

Расписание задаётся в формате `OnCalendar`: `daily`, `weekly`,
`Mon *-*-* 03:00:00`. Прогон по таймеру идёт с ограничением нагрузки
(`--pause-ms 200 --max-minutes 120`) и без индикатора.

### Как остановить сканирование

**Запущено в вашем терминале** — `Ctrl+C`. Docker передаёт сигнал внутрь
контейнера, процесс завершается, соединения с БД закрываются.

**Терминал закрыт или запускали из другой сессии:**

```bash
docker ps --format "{{.ID}}  {{.Image}}  {{.Status}}" | grep pii-scan
```

```bash
docker stop <ID>
```

`docker stop` даёт 10 секунд на завершение, затем убивает. Если ждать некогда —
`docker kill <ID>`.

**Прогон по расписанию systemd:**

```bash
sudo systemctl stop pii-scan.service
```

#### Снять нагрузку с БД

Остановка контейнера рвёт соединение, но **уже выполняющийся запрос СУБД может
доработать до конца**: MySQL замечает обрыв не мгновенно. Проверьте и при
необходимости снимите запрос вручную.

MySQL — найти и убить:

```sql
SHOW PROCESSLIST;
```

```sql
KILL QUERY 12345;
```

Вместо `12345` — `Id` строки, где `User` = `pii_reader`. `KILL QUERY` снимает
запрос, оставляя соединение; `KILL` рвёт и соединение.

Если запросов много, соберите команды одним запросом и выполните результат:

```sql
SELECT CONCAT('KILL QUERY ', id, ';') FROM information_schema.processlist WHERE user = 'pii_reader';
```

ClickHouse:

```sql
SELECT query_id, user, elapsed, formatReadableSize(memory_usage), query FROM system.processes WHERE user = 'pii_reader';
```

```sql
KILL QUERY WHERE user = 'pii_reader' SYNC;
```

Обычно до этого не доходит: сканер выставляет своим запросам серверный таймаут
(`MAX_EXECUTION_TIME` в MySQL, `max_execution_time` в ClickHouse — по умолчанию
15 секунд, параметр `query_timeout`). Даже если ничего не убивать руками,
осиротевшие запросы отвалятся сами в пределах этого времени. Долгих тяжёлых
запросов сканер не создаёт: каждый — это `SELECT … LIMIT 500` по одной таблице.

**Отчёты за прерванный прогон не сохраняются.** Это осознанно: частичная
выгрузка, неотличимая с виду от полной, в реестре ПДн опаснее, чем её
отсутствие. Если прогон нужно ограничить по времени, но с результатом —
используйте `--max-minutes`: по исчерпании бюджета сканер завершается
штатно и отчёты пишет.

### Частые ошибки при запуске

| Сообщение | Причина и решение |
|---|---|
| `каталог отчётов '/out' недоступен для записи` | контейнер запущен не под вашим uid — добавьте `--user "$(id -u):$(id -g)"`; либо `out/` принадлежит root, потому что установка шла от root: `sudo chown -R $USER out config .env` |
| `переменная окружения MYSQL_PWD не задана` | нет `.env` или он не передан: `--env-file .env` |
| `учётная запись имеет права на запись` | нужна read-only учётка; осознанно обойти — `--allow-rw` |
| `Access denied for user` | неверный пароль или учётке не выдан `GRANT SELECT` |
| `не установлен драйвер MySQL` | запущен не тот образ; пересоберите: `./install.sh` |
| `Port 9000 is for clickhouse-client program` | образ старее версии с выбором драйвера по порту: `git pull && ./install.sh` |
| `PermissionError: '/app/pii_scan/__init__.py'` | образ собран на сервере с `umask 077`, файлы внутри нечитаемы для непривилегированного пользователя — обновитесь и пересоберите: `git pull && ./install.sh` |
| Индикатор не появляется | нет `-t` у `docker run`, либо вывод перенаправлен в файл |
| Ключ вроде бы не работает, поведение прежнее | почти всегда старый образ: код обновился, а контейнер собран раньше. Первая строка вывода называет версию — сверьте с `git log`; лечится `git pull && ./install.sh` |
| В отчёте есть примеры значений, хотя их не просили | в вашем `config/config.yml` осталась строка `examples_per_hit: 3` от прежних версий — уберите её или поставьте `0` |

**Первая строка вывода — это версия работающего образа:**

```
pii-scan 0.2.0 | конфиг: /config/config.yml | источников: 2 | режим: выборка значений
```

Сверяйте её, прежде чем искать причину в другом месте: образ не
пересобирается сам, и «ключ не сработал» чаще всего означает, что запущена
прежняя сборка. Если примеры значений включены, следующая строка скажет и об
этом.

Коды возврата приведены в разделе «Ключи запуска».

## Отчёты

Четыре файла из таблицы в начале плюс то, что печатается в консоль. Ниже — как ими пользоваться.

### Что передать разработчикам

Сводка отвечает на вопрос «где искать», а разбивка по полям — на «что именно
и на каком основании». Ключ `--details` выводит её в консоль:

```
crm.employees   (источник prod-mysql)
  Поле               Тип      Вид ПДн                         Основание                Совпало  Увер.
  -----------------  -------  ------------------------------  -----------------------  -------  -----
  full_name          varchar  ФИО, ФИО в тексте (NER)         имя поля, значения, NER  120/120  100%
  passport           varchar  паспорт РФ (серия и номер)      имя поля, значения       120/120  80%
  diagnosis          varchar  сведения о состоянии здоровья   только имя поля          0/120    75%
  passport_seria     char     паспорт РФ (серия и номер)      только имя поля          0/120    35%
```

Колонка **Основание** объясняет вывод: `значения` — распознаны сами данные,
`NER` — имена найдены в свободном тексте, `имя поля` — сработало название или
комментарий к нему. **Совпало** — сколько значений выборки подтвердились.

Отдельно стоит **`только имя поля`**: содержимое читалось, но ни одно правило
в нём ничего не узнало. Это не то же самое, что находка, подтверждённая
данными, и работа с ней другая — смотреть не на что, надо выяснять у
разработчиков, что в поле лежит. Подробнее — [«Совпало 0, а уверенность
35 %»](#как-считается-уверенность).

Примеры значений в отчёт по умолчанию **не выносятся**: даже замаскированные,
они оставляют длину и формат. Нужны — добавьте `--examples` (три штуки) или
`--examples 5`. Столбец появляется только вместе с ключом.

То же самое в файлах, и для передачи разработчикам они удобнее:

* **`out/registry.xlsx`**, лист «Реестр» — строка на каждое поле с автофильтром:
  источник, СУБД, база, таблица, поле, тип, категория ПДн, вид ПДн,
  уверенность, основание, число совпадений. Лист «Требует проверки» —
  пограничные находки, их и отдают на ручной разбор: сверху подтверждённые
  содержимым, ниже держащиеся на одном названии поля;
* **`out/detailed.md`** — то же текстом, по таблицам;
* **`out/findings.json`** — для автоматической обработки.

Поля вида `params::$.client.phone` — это ключи внутри JSON-значения: видно не
только колонку, но и место внутри структуры.

#### Полная опись полей

По умолчанию в отчёт попадают только поля, где что-то нашлось. Ключ
`--full-inventory` добавляет **все поля всех обследованных таблиц**, включая
чистые — это подтверждение, что проверено всё, а не выборочно:

```
crm.employees   (источник prod-mysql)
  Поле               Тип      Вердикт           Вид ПДн                         Основание           Увер.
  -----------------  -------  ----------------  ------------------------------  ------------------  -----
  fio                varchar  ПДн               ФИО, ФИО в тексте (NER)         имя поля, значения  100%
  diagnosis          varchar  ПДн               сведения о состоянии здоровья   только имя поля     75%
  hired_at           date     требует проверки  дата рождения                   значения            50%
  id                 int      не обнаружено     —                               —                   —
  salary             decimal  не обнаружено     —                               —                   —
```

В реестре XLSX появляется лист **«Все поля»**: чистые поля залиты серым,
находки повышенной значимости — оранжевым. Именно этот лист удобнее всего отдавать
разработчикам: по нему видно и что нашли, и что смотрели.

Поля со слабым сигналом помечаются отдельно — например
`слабый признак: ИНН (30%)`. Это значит, что совпадение было, но до порога
уверенности не дотянуло: такие поля стоит глянуть глазами.

Опись заметно увеличивает объём отчётов (строка на каждое поле каждой
таблицы), поэтому включается только по требованию.

## Как работает поиск

Что именно ищется, как это настраивается и откуда берётся оценка уверенности.

### Что ищет

**По контрольной сумме** (ложных срабатываний практически нет): СНИЛС, ИНН
(10 и 12 знаков), полис ОМС, номер банковской карты.

**По формату** (контрольной суммы нет): паспорт РФ, загранпаспорт,
водительское удостоверение, банковский счёт, почтовый индекс, отдельная
фамилия или имя. Такие совпадения засчитываются всегда, но веса им хватает
только на «требует проверки» — колонка десятизначных кодов попадёт в отчёт
как возможный паспорт, и это осознанный размен: пропустить ПДн хуже, чем
вынести лишнее поле на ручной разбор.

**По значениям**: адрес электронной почты, телефон, адрес, ФИО целиком и по
частям, дата рождения.

**По свободному тексту (NER)**: ФИО и населённые пункты в комментариях,
описаниях, примечаниях — там, где ПДн заводятся незаметно и в реестр никогда
не попадают.

**По именам полей и комментариям**: то, что невозможно распознать по
содержимому. «Русский», «гипертония», «супруга» — обычные слова, отличимой
формы у них нет, и единственный признак это название поля или комментарий к
нему. Такое имя вывод и решает: `diagnosis` двусмысленности не оставляет, а
цена пропуска высока — непустая колонка сразу считается ПДн.

Это **не** отсев по имени: значения такой колонки читаются и проверяются
всеми остальными правилами наравне с любыми другими, см. [Имя поля не
участвует в отсеве](#имя-поля-не-участвует-в-отсеве). Полный перечень правил
задан в `pii_scan/detectors.py`.

**Внутри JSON**: значение разбирается рекурсивно, каждый ключ становится
виртуальной колонкой. В отчёте это выглядит как `payload::$.client.phone` —
видно не только что в колонке есть ПДн, но и где именно внутри структуры.

### Какая часть таблицы читается

Не вся. По умолчанию из каждой таблицы читается **500 строк** — этого хватает,
чтобы понять, что за данные лежат в колонке, и не хватает, чтобы уронить прод.
Полный скан здесь и не нужен: ПДн — свойство поля, а не отдельной строки, и
решение принимается по доле совпавших значений, а не по их полному перечню.

| Что ограничивает | Параметр (конфиг / ключ) | По умолчанию |
|---|---|---|
| строк на таблицу | `sample_limit` / `--limit` | 500 |
| откуда берутся строки | `sample_strategy` / `--strategy` | `head_tail` |
| трафик на таблицу | `max_bytes_per_table` | 2 МБ |
| длина одного значения | `max_value_len` | 512 символов |
| значений на колонку для NER | `ner_values_per_column` | 50 |

**Половина выборки берётся с конца таблицы.** Чтение только «головы» —
систематическая слепая зона: поле, которое начали заполнять полгода назад, в
старых строках пусто, и сканер объявит его чистым. Поэтому по умолчанию
работает `head_tail`: 250 строк с начала и 250 с конца, по первичному ключу или
ключу сортировки. Если ключа нет (представление, таблица без PK), читается
только голова — сортировать не по чему.

**Таблица меньше выборки читается целиком** и ровно один раз: если в ней 80
строк, обе части выборки не сложатся в 160 запросов на те же данные.

**Широкая таблица читается мельче.** Ограничение идёт по трафику, а не по
строкам: у таблицы на 300 колонок 500 строк — это десятки мегабайт по сети,
поэтому сканер сам возьмёт меньше строк, оставаясь в пределах
`max_bytes_per_table`. Длинные значения обрезаются **на стороне БД** — по сети
приходит не blob целиком, а первые 512 символов.

**У NER свой бюджет** — 50 значений на колонку вместо 500. Модель на порядок
медленнее регулярных выражений, а ей достаточно факта: если ФИО в примечаниях
есть, они найдутся и в первых полусотне записей.

Что это значит для результата: **редкие** ПДн — одна строка на миллион —
выборка может не увидеть. Лечится точечно, а не глобальным увеличением лимита:

```bash
pii-scan --limit 20000 --only prod-mysql --details
```

### Выбор категорий

По умолчанию ищутся **все** категории. Если нужна только часть — например
инвентаризация одних ФИО — перечислите категории в конфиге:

```yaml
scan:
  detectors: [names]
```

или ключом при запуске:

```bash
pii-scan --detectors names,contacts
```

Категории объединяют правила в группы. Основные:

| Категория | Что входит |
|---|---|
| `names` | ФИО целиком, отдельные части имени, ФИО в свободном тексте (NER) |
| `contacts` | почта, телефон, адрес, почтовый индекс, населённые пункты в тексте |
| `documents` | СНИЛС, ИНН, полис ОМС, паспорт, загранпаспорт, ВУ, свидетельство о рождении |
| `finance` | номер банковской карты, банковский счёт |
| `birth` | дата и место рождения |

Названия задаются латиницей: в конфигах и командной строке кириллица легко
ломается на кодировках. Русские написания (`фио`, `контакты`, `документы`…)
принимаются как псевдонимы, чтобы уже написанные конфиги продолжали работать,
но в примерах и документации используется латиница.

В отчёты при этом попадают **русские** названия: «Искали: ФИО, контакты» —
документ читает проверяющий, а не тот, кто правил конфиг.

Вместо группы можно указать отдельное правило — например `snils` или
`bank_card`.

Таблица перечисляет основные группы. **Полный перечень — вместе с теми
группами, которых здесь нет, и со всеми правилами поштучно — печатает сам
сканер:**

```bash
pii-scan --list-detectors
```

Дублировать каталог целиком в документации смысла нет: он задан в
`pii_scan/detectors.py` и меняется вместе с кодом, а копия разошлась бы с ним
при первом же изменении — это уже происходило.

**Отключаются правила, а не колонки.** Значения всех полей читаются и
проверяются как обычно, из работы выводятся только правила невыбранных
категорий. При `--detectors names` колонка с почтой по-прежнему читается,
но правило «адрес электронной почты» к ней не применяется — поэтому в
отчёте она получает вердикт «не обнаружено», а не исчезает из охвата.

Имя колонки на решение «проверять или нет» по-прежнему не влияет: выборка из
базы не меняется, объём чтения тот же. Единственное, что реально ускоряется, —
NER: если распознавание по свободному тексту не входит в выбранные категории,
модель не загружается и не запускается.

**Ограниченный охват помечается в отчёте.** В шапке появляется строка
«Искали: ФИО» и предупреждение, что отчёт нельзя считать полным
обследованием: иначе выборочную проверку легко принять за полную.

### Как считается уверенность

Свидетельства независимы и складываются:

```
доля  = совпавших значений / содержательных значений колонки
score = min(1, доля / 0.5) × вес правила
        + 0.35, если сработало имя поля или комментарий к нему
```

Две особенности этой формулы объясняются одной фразой каждая.

**Половина колонки — уже полная уверенность** (это и есть деление на 0.5).
Выше половины уточнять нечего: колонка, где ПДн в каждом втором значении,
носитель персональных данных ничуть не меньше, чем колонка, где они в
каждом. Линейная доля отвечала на вопрос «всё ли поле — ПДн», тогда как для
152-ФЗ важно «есть ли в поле ПДн».

**Заглушки не считаются.** `-`, `н/д`, `не указан`, `NULL`, `нет данных` —
это записанное отсутствие значения, а не другое значение. В знаменателе им
места нет, иначе наполовину заполненная колонка телефонов выглядит
наполовину чужой. Неоднозначные `0`, `нет`, `x` заглушками **не** считаются:
ошибка в эту сторону завышала бы долю. Знаменатель при этом не опускается
ниже десятой части прочитанного — колонка из пятисот «н/д» и одного телефона
иначе давала бы стопроцентную уверенность.

* **≥ 70 %** — ПДн, попадает в лёгкий отчёт и в реестр;
* **35–70 %** — требует ручной проверки;
* **< 35 %** — в отчёт не выносится (но виден в полной описи как «слабый признак»).

**Доля — основа оценки, а не оттенок.** Единичное попадание и сплошная
колонка получают разные вердикты, а не разные проценты одного и того же
вывода:

| Совпало из 500 | Оценка | Вердикт | Как это читать |
|---|---|---|---|
| 1 | 0 % | не обнаружено | опечатка, чужое значение в чужом поле |
| 25 | 10 % | не обнаружено | примесь, а не назначение поля |
| 50 | 20 % | не обнаружено | десятая часть — ещё не закономерность |
| 100 | 40 % | требует проверки | пятая часть колонки — уже вопрос |
| 250 | **100 %** | **ПДн** | половина: шкала насыщается |
| 485 | **100 %** | **ПДн** | поле для того и заведено |

Смысл ровно тот, что подсказывает здравый смысл: **один СНИЛС в поле
комментария — это инцидент ввода, а двести СНИЛС — это колонка СНИЛС.**
Первое не должно попадать в реестр ПДн, но и потеряться не должно —
единичные совпадения видны в полной описи с точным счётом:

```
| `comment` | text | не обнаружено | слабый признак: СНИЛС (1 из 500) |
```

Показывается именно счёт, а не процент: у одного значения из пятисот доля
округляется до «0 %», и вся информация пропадает.

**Пустые значения и заглушки не размывают долю.** Знаменатель — только
содержательные значения. Колонка, где 490 из 500 строк `NULL`, а все 10
заполненных — телефоны, получит 100 %, а не 2 %. То же и с текстовыми
заглушками: 319 телефонов и 360 прочерков — это 100 %, а не 47 %.

**Потолок задаёт вес правила, и насыщение его не поднимает.** Колонка
сплошных десятизначных чисел совпадает с форматом паспорта на все 100 %, но
контрольной суммы у этого правила нет — вес 0.45, и выше «требует проверки»
такая колонка не поднимется ни при какой доле. Это и защищает от ложных
срабатываний на технических идентификаторах.

**«Совпало 0, а уверенность 35 %» — это не ошибка.** Имя совпало, значения
не подтвердили — ровно 0,35, то есть впритык к порогу «требует проверки».
Порог не понижен намеренно: такое чаще означает **разрыв в правилах**, а не
ложное срабатывание. Живой пример со стенда:

```
crm.clients.passport_seria  char(4)  8148, 4881, 4767 …   0/500  35%
crm.clients.passport_nomer  char(6)  377139, 222143 …     0/500  35%
```

Это настоящие паспортные данные. Совпадений нет потому, что правило ищет
серию и номер вместе, а схема разнесла их по двум колонкам: четыре цифры
сами по себе — просто четыре цифры. Понизь мы вес имени — эти поля ушли бы
в «не обнаружено». Так же ведёт себя `last_name` с латиницей: правила ФИО
работают по кириллице, «Smith» им не опознать.

Поэтому вместо понижения оценки разбор **разделён по основанию** — работа
там разная:

```
  Требуют проверки:        0 табл. / 9 полей
    подтверждено значениями: 7      ← смотреть содержимое глазами
    только по имени поля:    2      ← спрашивать у разработчиков, что внутри
```

В реестре (`registry.xlsx`, лист «Требует проверки») поля отсортированы так
же: сначала подтверждённые содержимым, ниже — держащиеся на одном названии,
у них в колонке «Совпало значений» стоит `0/500`.

Счёт идёт по **полям, а не по таблицам**: `passport_seria` лежит в таблице,
где ФИО уже нашлись, поэтому сама таблица давно числится «с ПДн» — но поле
разбирать всё равно придётся.

**Имя поля усиливает вывод, но не является условием.** Значения проверяются
у каждой колонки независимо от того, как она называется: поле
`rp_responsible` с фамилиями будет найдено так же, как `last_name`. Разница
только в итоговой уверенности — говорящее имя добавляет те самые 35 %.

Обратная сторона: колонка городов (Ростов, Псков, Киров неотличимы от
фамилий по значению) выйдет в «требует проверки». Это сознательный выбор в
пользу полноты: для 152-ФЗ пропущенное поле дороже лишней строки на
проверку.

Часть правил делает вывод по имени поля — там, где распознать значение
нечем. Имена в таких случаях однозначные, а цена пропуска высокая, поэтому
непустое поле сразу считается ПДн, пустое уходит на проверку.

### Имя поля не участвует в отсеве

Читаются и проверяются **все** колонки всех таблиц. Ни одна не пропускается
из-за того, что называется неудачно: `field_23`, `col7`, `data` обследуются
ровно так же, как `client_fio`.

Имя поля — один из трёх независимых каналов свидетельств, а не фильтр перед
ними:

| Канал | Что даёт |
|---|---|
| имя колонки и комментарий | `+0.35` к оценке; для нескольких правил — сразу вывод |
| значения из выборки | доля совпавших × вес правила |
| NER по свободному тексту | факт присутствия ФИО или топонима |

Каналы складываются, и **любого из них хватает самостоятельно**. Колонка
`rp_responsible` с фамилиями попадёт в отчёт по значениям, хотя её имя не
совпадает ни с одним правилом. Колонка `diagnosis` попадёт по имени, хотя
диагноз словами распознать нечем.

Из 22 правил **19 работают по содержимому**: 17 разбирают само значение,
ещё 2 — распознают ФИО и топонимы в свободном тексте. Оставшиеся три —
место рождения, национальность и подобное, родственники — описывают данные,
у которых нет отличимой формы: «русский» неотличим от любого другого слова.
Такое правило не срабатывает по значению просто потому, что срабатывать
не на чем, — но остальные 19 по этой колонке отрабатывают в полном объёме,
и ФИО родственника в ней найдётся правилом «ФИО», а не правилом
«родственники».

Проверить это на своей базе можно так:

```bash
pii-scan --full-inventory --details
```

В отчёт попадут **все** поля, включая те, где ничего не найдено, — с
указанием, сколько значений просмотрено. Это и есть доказательство охвата:
у чистой колонки будет видно «просмотрено 500», а не пропуск.

## Работа на проде

Сканер рассчитан на обследование работающих баз. Что для этого сделано и чем управлять, если база большая или нагруженная.

### Что делается для безопасности прода

* `COUNT(*)` не выполняется никогда — размер берётся из `information_schema` /
  `system.tables`;
* одна выборка на таблицу, а не по запросу на колонку;
* значения обрезаются **на стороне сервера** (`LEFT(CAST(...))`,
  `substring(toString(...))`) — по сети не едут мегабайтные тексты;
* жёсткий таймаут запроса и ограничение `max_threads`;
* никаких `ORDER BY RAND()` — только `LIMIT`;
* `Distributed`, `Merge` и представления в ClickHouse пропускаются: иначе одни
  и те же данные попадут в отчёт по нескольку раз;
* **примеры значений в отчёт не попадают вовсе.** Даже маска
  (`ив****@ex***e.com`) оставляет длину, формат и первые символы, а отчёт
  уходит разработчикам и внешним проверяющим. Нужны примеры — просите явно:
  `--examples` (три штуки) или `--examples 5`. Столбец появляется в отчётах
  только вместе с ключом, пустым не стоит;
* `--show-values` снимает и маскировку — отчёт становится полноценным
  носителем ПДн со всеми вытекающими требованиями к его хранению.

### Ограничение нагрузки

Главная опасность для работающей базы — не процессор, а вымывание буферного
пула: сканер читает первые страницы каждой таблицы, и они вытесняют горячие
данные приложения. Сдерживать это можно тремя способами.

```yaml
throttle:
  pause_ms: 200               # пауза между запросами
  max_queries_per_minute: 60  # либо потолок темпа
  max_duration_min: 30        # бюджет времени: по исчерпании прогон
                              # завершается корректно и сохраняет найденное
```

Те же параметры доступны ключами `--pause-ms`, `--max-qpm`, `--max-minutes`.

Дополнительно у каждого источника есть проброс настроек сессии — это точное
управление уже средствами самой СУБД:

```yaml
sources:
  - name: prod-clickhouse
    type: clickhouse
    settings:
      max_bytes_to_read: 100000000        # жёсткий потолок чтения на запрос
      max_execution_speed_bytes: 20000000 # родное ограничение скорости, байт/с
      max_memory_usage: 1000000000
      priority: 10                        # фоновый приоритет запросов

  - name: prod-mysql
    type: mysql
    settings:
      max_execution_time: 5000            # мс
```

Рекомендуемый порядок на проде:

1. `--dry-run` — только схема, ни одной строки данных. Уже покажет
   поля, названные явно.
2. Полный прогон на **реплике**, если она есть, — там вымывание кэша никому
   не мешает.
3. Если реплики нет — ночное окно, `--pause-ms 200 --max-minutes 60` и
   `--limit 200`. Прогон, оборванный по бюджету, не теряет результат.

* Инструмент работает по **выборке** — по умолчанию 500 строк с начала и с
  конца таблицы, см. [Какая часть таблицы
  читается](#какая-часть-таблицы-читается). ПДн, встречающиеся в единичных
  строках, он может не увидеть — увеличивайте `--limit` для подозрительных
  таблиц точечно.
* Диагнозы, национальность и подобные сведения **словами** распознать
  нечем: «гипертония» для regex неотличима от любого другого слова. Такое
  поле находится по имени или комментарию — а если названо `field_23` и не
  прокомментировано, найдётся только когда в нём лежат коды МКБ-10 (`I10`,
  `E11.9`) или что-то ещё распознаваемое. Речь именно о нераспознаваемых
  значениях: сама колонка читается и проверяется всегда, см. [Имя поля не
  участвует в отсеве](#имя-поля-не-участвует-в-отсеве).
* Контрольная сумма отсекает подавляющее большинство мусора, но около 1/11
  случайных десятизначных чисел формально проходят проверку ИНН. Гасится это
  долей совпадений по колонке: одно валидное значение из трёхсот находкой не
  становится.
* Кириллица в MySQL, записанная через соединение с неверной кодировкой
  (`Ð“Ð¾Ð»ÑƒÐ±ÐµÐ²` вместо `Голубев`), распознаётся и восстанавливается для
  анализа — иначе в legacy-базе сканер молча пропустил бы все ФИО и адреса.
  В отчёт при этом добавляется предупреждение: саму базу это не чинит.
* Результат — **основание для проверки, а не юридическая квалификация**.
  Решение об отнесении сведений к персональным данным принимает оператор.

### Большие базы и сложные схемы

Стоимость прогона определяется не гигабайтами, а числом объектов: 50 ГБ в
двадцати таблицах — это двадцать запросов, те же 50 ГБ в пяти тысячах
партиций — пять тысяч. Поэтому масштабирование идёт по объектам.

**Однотипные таблицы обследуются по образцу.** `orders_2016_01 … orders_2025_12`
или `sessions_shard_00 … shard_63` — одна структура. Сканер группирует их по
имени с точностью до чисел **и по совпадению набора полей**, читает пару самых
крупных представителей, а остальным переносит объединённый результат с пометкой
«по образцу» в отчёте. Отключается флагом `--no-grouping`.

**Вероятное обследуется первым.** Таблицы, где имена полей уже намекают на ПДн,
идут в начале очереди. Если прогон оборвётся по времени, в отчёт успеет попасть
именно то, ради чего он запускался.

**Широкие таблицы читаются мельче.** Выборка ограничивается не числом строк, а
трафиком: `max_bytes_per_table` (по умолчанию 2 МБ). У таблицы на 300 колонок
сканер сам возьмёт меньше строк вместо десятков мегабайт по сети.

#### Замеры на стенде

285 таблиц, 1277 колонок в MySQL (120 помесячных партиций, 64 шарда,
100 справочников, таблица на 120 колонок) плюс ClickHouse:

| Режим | Обследовано таблиц | Время |
|---|---|---|
| Без группировки | 290 из 290 | 18.8 с |
| С группировкой (по умолчанию) | **12 из 290**, остальные по образцу | 10.5 с |
| Пауза 200 мс между запросами | 12 | 13.2 с |
| Бюджет 1 мин, пауза 300 мс, без группировки | 188 из 290, остановлен по времени | 67 с |

Во всех четырёх режимах найден один и тот же набор таблиц с ПДн — включая
прогон, оборванный по бюджету: приоритизация вывела нужное вперёд, а
пропущенными оказались справочники без персональных данных.

## Справочник

Полный перечень ключей и кодов возврата.

### Ключи запуска

```
--config PATH             путь к конфигу (в контейнере /config/config.yml)
--out DIR                 каталог отчётов (по умолчанию /out)
--formats СПИСОК          summary,detailed,json,xlsx или all
--dry-run                 только схема, значения не читаются
--limit N                 строк выборки на таблицу
--strategy head|tail|head_tail   откуда брать выборку
--only ИМЯ                только указанный источник (можно повторять)
--no-ner                  отключить NER по свободному тексту
--no-json                 не разбирать JSON внутри значений
--allow-rw                разрешить учётную запись с правами на запись
--details / -d            разбивка по полям прямо в консоли
--full-inventory          в отчёты все поля всех таблиц, включая чистые
--detectors СПИСОК        какие категории искать: names, contacts, …
--list-detectors          показать доступные категории и правила
--examples [N]            показать N замаскированных примеров (без числа — 3;
                          по умолчанию примеры не показываются)
--show-values             не маскировать примеры (отчёт станет носителем ПДн)
--progress auto|on|off    индикатор выполнения
-q / -v                   тише / подробнее

Ограничение нагрузки:
--pause-ms МС             пауза между запросами к БД
--max-qpm N               не больше N запросов в минуту
--max-minutes МИН         бюджет времени на прогон
--no-grouping             не наследовать результат на однотипные таблицы
```

Полный список — `pii-scan --help`.

Коды возврата: `0` — успех, `1` — были ошибки при сканировании, `2` — ошибка
конфигурации, `3` — запуск заблокирован из-за прав на запись.

## Разработка

Как поднять стенд, прогнать тесты и добавить новую СУБД.

### Тестовый стенд

Для проверки инструмента есть генератор синтетических данных — вымышленные
ФИО и адреса, валидные по контрольным суммам СНИЛС/ИНН/ОМС/карты, ПДн внутри
JSON и в свободном тексте, плюс намеренные ловушки на ложные срабатывания
(технические коды, журналы, метрики, настройки).

```bash
cd testdata && python generate.py . && docker compose -f docker-compose.test.yml up -d
```

Поднимутся MySQL с базой `crm`, PostgreSQL с базой `shop` (две схемы —
`crm` и `ops`) и ClickHouse с базой `analytics` в сети `pii-test-net`, вместе
с учётными записями `pii_reader` (только чтение) и `app_rw` / `etl_writer`
(с правами на запись — для проверки блокировки).
Сканер запускается в той же сети:

```bash
docker run --rm --network pii-test-net --user "$(id -u):$(id -g)" -v "$PWD/config:/config:ro" -v "$PWD/out:/out" -e MYSQL_PWD='ReadOnly_2026!' -e CH_PWD='ReadOnly_2026!' pii-scan:full --config /config/config.yml
```

### Сборка и тесты

```bash
python -m venv .venv && . .venv/bin/activate
pip install -r requirements.txt -r requirements-nlp.txt pytest
python -m pytest tests -q
```

Правила распознавания целиком лежат в `pii_scan/detectors.py` — это единственное
место, где живёт знание о ПДн, и оно не делает ввод-вывод, поэтому тестируется
без всякой БД. Новый тип СУБД добавляется одним файлом в `pii_scan/sources/`.
