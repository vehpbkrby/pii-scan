# pii-scan

Поиск персональных данных (152-ФЗ) в **MySQL** и **ClickHouse**. Отвечает на
один вопрос: в каких таблицах и полях лежат ПДн, каких категорий и насколько
можно доверять выводу.

Утилита ничего не пишет в обследуемые БД, никуда не передаёт данные по сети и
не маскирует поля — только находит и документирует.

## Что на выходе

| Файл | Назначение |
|---|---|
| `summary.md` | Лёгкий отчёт: только уверенные находки, строка на таблицу. Для владельца системы и руководителя. |
| `detailed.md` | Подробный отчёт: все находки, включая пограничные, с основанием вывода и замаскированными примерами. |
| `registry.xlsx` | Реестр: листы «Реестр», «Требует проверки», «Сводка». Автофильтр, спецкатегории подсвечены. |
| `findings.json` | Полная выгрузка со всеми оценками — для скриптов и сравнения прогонов. |

## Установка

```bash
git clone https://github.com/vehpbkrby/pii-scan.git && cd pii-scan
./install.sh
```

Скрипт проверит docker и место на диске, создаст `config/` и `out/`, положит
`config.yml` и `.env` из примеров (`.env` с правами 600), соберёт образ и
поставит команду `pii-scan` — обёртку над `docker run` с нужными томами,
`--user` и выделением терминала под индикатор выполнения.

| Ключ | Что делает |
|---|---|
| `./install.sh` | образ с NER (276 МБ) |
| `./install.sh --slim` | образ без NER (164 МБ) — для закрытого контура |
| `./install.sh --systemd weekly` | плюс регулярный прогон по расписанию systemd |
| `./install.sh --uninstall` | убрать команду и юниты (образ и отчёты остаются) |

Команда ставится в `/usr/local/bin`, если есть root или беспарольный sudo,
иначе в `~/.local/bin`.

### Если install.sh не видит docker

Две самые частые причины, обе неочевидные:

**Демон не запущен.** `systemctl enable docker` только прописывает автозапуск
при загрузке, но сам сервис не поднимает:

```bash
sudo systemctl start docker
```

**Группа выдана, но не применилась.** `usermod -aG docker` меняет базу групп,
однако уже запущенная сессия свой список групп не перечитывает — он выдаётся
при входе в систему. Поэтому в том же терминале доступа по-прежнему нет:

```bash
newgrp docker                 # применить в текущей сессии
sg docker -c ./install.sh     # либо сразу запустить установку
```

Либо выйти из системы и зайти заново. Проверить, что обе причины закрыты:

```bash
systemctl is-active docker && id -nG | tr ' ' '\n' | grep -x docker && docker info >/dev/null && echo ок
```

Установщик различает эти случаи и подсказывает нужную команду — если он
сообщает что-то другое, читайте его вывод, там конкретика.

### Корпоративный TLS-инспектор

Если сборка падает так:

```
[SSL: CERTIFICATE_VERIFY_FAILED] certificate verify failed:
self-signed certificate in certificate chain
ERROR: No matching distribution found for wheel
```

значит, трафик разбирает корпоративный TLS-инспектор: он подменяет
сертификат pypi.org своим. Сам сервер этому корню доверяет, а контейнер при
сборке — ещё нет, у него собственное хранилище. Передайте связку сертификатов
хоста в сборку:

```bash
./install.sh --ca-cert /etc/ssl/certs/ca-certificates.crt
```

Установщик положит её в контекст сборки как `ca-cert.crt` (файл в
`.gitignore`), образ добавит сертификат в системное хранилище и укажет его
pip через `PIP_CERT` — **pip проверяет сертификаты по связке certifi, а не по
системному хранилищу**, поэтому одного `update-ca-certificates` мало.

Если PyPI закрыт полностью, а внутреннее зеркало есть:

```bash
./install.sh --pip-index https://nexus.corp/repository/pypi/simple --trusted-host nexus.corp
```

При сборке вручную это те же аргументы:

```bash
docker build --build-arg WITH_NLP=1 --build-arg PIP_INDEX_URL=... --build-arg PIP_TRUSTED_HOST=... -t pii-scan:full .
```

### Сервер без доступа в интернет

Сборка образа — единственный шаг, которому нужен интернет (pip тянет
зависимости). В закрытом контуре соберите образ на машине с доступом и
перенесите файлом:

```bash
docker build --build-arg WITH_NLP=1 -t pii-scan:full .     # там, где есть интернет
docker save pii-scan:full | gzip > pii-scan-full.tar.gz
```

```bash
gunzip -c pii-scan-full.tar.gz | docker load               # на закрытом сервере
./install.sh --skip-build
```

Расписание для `--systemd` — в формате `OnCalendar`: `daily`, `weekly`,
`Mon *-*-* 03:00:00`. Прогон по таймеру запускается с ограничением нагрузки
(`--pause-ms 200 --max-minutes 120`) и без индикатора; журнал —
`journalctl -u pii-scan.service`.

### Установка вручную

Если установщик не подходит, достаточно собрать образ и подготовить каталоги:

```bash
cp .env.example .env                       # пароли к БД
mkdir -p config out && cp config.example.yml config/config.yml
docker build --build-arg WITH_NLP=1 -t pii-scan:full .
```

## Как запустить

### Первый запуск, по шагам

**1. Впишите пароли** — в конфиге их быть не должно, только ссылки `${VAR}`:

```bash
$EDITOR .env
```

```
MYSQL_PWD=пароль_учётки_pii_reader
CH_PWD=пароль_учётки_pii_reader
```

**2. Укажите, что обследуем** — адреса, учётные записи, при необходимости
фильтры баз и таблиц:

```bash
$EDITOR config/config.yml
```

Минимально достаточно этого:

```yaml
sources:
  - name: prod-mysql
    type: mysql
    host: 10.0.0.10
    user: pii_reader
    password: ${MYSQL_PWD}
```

Список таблиц перечислять не нужно — сканер сам прочитает структуру.

**3. Сухой прогон.** Читается только схема: имена таблиц, полей и комментарии.
**Ни одна строка данных не читается**, нагрузки на базу практически нет.

```bash
pii-scan --dry-run
```

Так проверяется и связь, и права, и охват — и уже видно спецкатегории с
родственниками. На прод всегда заходите с этого.

**4. Полный прогон** — с чтением выборки значений:

```bash
pii-scan
```

**5. Заберите отчёты** из каталога `out/`:

```
out/summary.md      лёгкий отчёт: только уверенные находки
out/detailed.md     подробный: все находки с основанием и примерами
out/registry.xlsx   реестр с автофильтром
out/findings.json   полная выгрузка для скриптов
```

Имена файлов постоянные, каждый прогон их перезаписывает. Две оговорки:

* с `--formats xlsx` (или любым неполным списком) остальные файлы **не
  обновляются и не удаляются** — в каталоге останутся отчёты от прошлого
  прогона со старой датой. Сверяйтесь с датой изменения или чистите `out/`;
* чтобы сохранить историю, копируйте `out/` с датой в имени — сравнение
  `findings.json` между прогонами показывает, что появилось нового.

### Что видно во время работы

```
13:20:41 INFO    Конфиг: /config/config.yml | источников: 2 | режим: выборка значений
13:20:41 INFO    Источник 'prod-mysql': таблиц 286, к обследованию 12, по образцу 274
prod-mysql [████████░░░░░░░░░░░░░░░░] 59/286  21% · осталось ~4 с  big.orders_2020_11
```

По завершении в консоль выводится сводка: сколько таблиц с ПДн, сколько со
спецкатегориями, сколько требует ручной проверки.

### Типовые сценарии

| Задача | Команда |
|---|---|
| Первичная инвентаризация, не трогая данные | `pii-scan --dry-run` |
| Полное обследование | `pii-scan` |
| Только один источник | `pii-scan --only prod-mysql` |
| Точечно, с большой выборкой | `pii-scan --limit 20000 --only prod-mysql` |
| Ночной прогон с ограничением нагрузки | `pii-scan --pause-ms 200 --max-minutes 120` |
| Быстрая прикидка без NER | `pii-scan --limit 100 --no-ner` |
| Только реестр XLSX | `pii-scan --formats xlsx` |
| Каждая таблица отдельно, без наследования | `pii-scan --no-grouping` |
| Свежие записи вместо старых | `pii-scan --strategy tail` |

### Если установщик не использовался

Через compose:

```bash
PII_UID=$(id -u) PII_GID=$(id -g) docker compose run --rm scanner --config /config/config.yml --dry-run
```

Через `docker run` напрямую:

```bash
docker run --rm -t --user "$(id -u):$(id -g)" --env-file .env -v "$PWD/config:/config:ro" -v "$PWD/out:/out" pii-scan:full --config /config/config.yml --dry-run
```

Что здесь важно:

* `--user "$(id -u):$(id -g)"` — внутри образа пользователь с uid 10001, без
  этого каталог `out/` окажется недоступен для записи. Права проверяются **до**
  сканирования, а не после: иначе многочасовой прогон терял бы результат на
  последнем шаге.
* `-t` — иначе не будет индикатора выполнения.
* `config` монтируется только на чтение, `out` — единственная точка записи.

### Если БД не видна из контейнера

| Ситуация | Что делать |
|---|---|
| БД на другом сервере | ничего, работает как есть |
| БД в docker-сети | `PII_NETWORK=имя_сети pii-scan` |
| БД на 127.0.0.1 того же хоста | `network_mode: host` в `docker-compose.yml` |
| Не резолвится имя хоста | `extra_hosts` в `docker-compose.yml` |

### Регулярные прогоны

```bash
./install.sh --systemd weekly
systemctl list-timers pii-scan.timer     # когда ближайший запуск
journalctl -u pii-scan.service           # как прошёл прошлый
```

Отчёты перезаписываются на каждом прогоне, поэтому при работе по расписанию
имеет смысл складывать их в архив. Добавьте в
`/etc/systemd/system/pii-scan.service` строку (знак процента в юнитах
удваивается):

```ini
ExecStartPost=/bin/sh -c 'cp -a out "archive/$(date +%%Y-%%m-%%d)"'
```

### Частые ошибки при запуске

| Сообщение | Причина и решение |
|---|---|
| `каталог отчётов '/out' недоступен для записи` | контейнер запущен не под вашим uid — добавьте `--user "$(id -u):$(id -g)"` |
| `переменная окружения MYSQL_PWD не задана` | нет `.env` или он не передан: `--env-file .env` |
| `учётная запись имеет права на запись` | нужна read-only учётка; осознанно обойти — `--allow-rw` |
| `Access denied for user` | неверный пароль или учётке не выдан `GRANT SELECT` |
| `не установлен драйвер MySQL` | запущен не тот образ; пересоберите: `./install.sh` |
| Индикатор не появляется | нет `-t` у `docker run`, либо вывод перенаправлен в файл |

Коды возврата приведены в разделе «Ключи запуска».

## Сборка образа

```bash
docker build -t pii-scan:slim .                          # 164 МБ, только regex
docker build --build-arg WITH_NLP=1 -t pii-scan:full .   # 276 МБ, + NER
```

Размеры измерены на Ubuntu 25.10, Docker 28.2.

`docker compose` собирает вариант из переменной `WITH_NLP` в `.env` (по
умолчанию — с NER). Для закрытого контура удобнее `slim`: в нём нет моделей и
объяснять безопасникам лишние 500 МБ весов не придётся.

База образа — `python:3.10-slim`. Это не случайность: `natasha` тянет
`pymorphy2`, который использует `inspect.getargspec`, удалённый в Python 3.11.

Модели NER (`navec`, `slovnet`) упакованы внутрь пакета `natasha` и ставятся
на этапе сборки. **В рантайме доступ в интернет не нужен**: инференс идёт
локально на CPU, HTTP-клиента в коде нет. Контейнеру нужен доступ только к
портам обследуемых СУБД.

## Подключение по сети

Сканер подключается к СУБД по обычному сетевому соединению — БД могут стоять
на других серверах, локально ничего разворачивать не нужно.

| СУБД | Порт по умолчанию | Протокол | Драйвер |
|---|---|---|---|
| MySQL / MariaDB | 3306 | родной протокол MySQL | PyMySQL (запасной — mysql-connector) |
| ClickHouse | 8123 (HTTPS — 8443) | HTTP | clickhouse-connect |
| ClickHouse | 9000 (TLS — 9440) | нативный | clickhouse-driver, если первого нет |

TLS включается флагом `secure: true`; при необходимости укажите корневой
сертификат `ssl_ca` (путь **внутри контейнера**, положите файл в `config/`) и
`ssl_verify: false`, если сертификат самоподписанный и проверять его не нужно.

Что важно в Docker:

* **БД на другом сервере** — работает как есть, ничего настраивать не надо.
* **БД на том же хосте, слушает 127.0.0.1** — из контейнера этот адрес указывает
  на сам контейнер. Раскомментируйте `network_mode: host` в
  `docker-compose.yml` либо используйте `host.docker.internal` вместе с
  `extra_hosts: ["host.docker.internal:host-gateway"]`.
* **Доступ по имени хоста из внутренней DNS** — если контейнер её не видит,
  пропишите адреса через `extra_hosts` в compose-файле.

Наружу, в интернет, утилита не ходит: HTTP-клиента в коде нет, модели NER
загружаются с диска. Контейнеру достаточно доступа к портам обследуемых СУБД.

## Учётные записи в БД

Сканеру нужен **только SELECT**. Наличие прав на запись блокирует запуск —
это защита от прогона под административной учёткой на проде.

### MySQL

```sql
CREATE USER 'pii_reader'@'10.0.0.%' IDENTIFIED BY 'СЛОЖНЫЙ_ПАРОЛЬ';
GRANT SELECT ON *.* TO 'pii_reader'@'10.0.0.%';
```

Используются: `information_schema.TABLES` и `information_schema.COLUMNS` для
структуры, `SHOW GRANTS FOR CURRENT_USER()` для проверки режима только чтения,
`SELECT` для выборки значений. Отдельные привилегии на `information_schema`
выдавать не нужно, но помните: MySQL показывает там только те объекты, на
которые у пользователя есть хоть какие-то права. Если выдать SELECT лишь на
одну базу, остальные сканер попросту не увидит — это удобный способ ограничить
охват. `PROCESS`, `SUPER`, `RELOAD` не нужны.

Чтобы обследовать не весь сервер:

```sql
GRANT SELECT ON crm.* TO 'pii_reader'@'10.0.0.%';
GRANT SELECT ON billing.* TO 'pii_reader'@'10.0.0.%';
```

### ClickHouse

```sql
CREATE USER pii_reader IDENTIFIED WITH sha256_password BY 'СЛОЖНЫЙ_ПАРОЛЬ'
    SETTINGS readonly = 2;
GRANT SELECT ON *.* TO pii_reader;
```

`readonly = 2`, а не `1`: сканер выставляет для своих запросов
`max_execution_time` и `max_threads`, чтобы не нагружать сервер, — при
`readonly = 1` сервер запретит менять настройки и запросы упадут.

Используются `system.tables` и `system.columns` (видны объекты, к которым есть
доступ), `system.settings` для проверки режима readonly, `SHOW GRANTS` и
`SELECT`. Права `ADMIN`, `SYSTEM`, `INTROSPECTION` не нужны.

### Если учётка с правами на запись

Запуск блокируется с кодом возврата `3` и перечнем найденных привилегий.
Обойти можно флагом `--allow-rw` — в отчёте и в консоли останется отметка, что
источник сканировался не в режиме только чтения.

## Что ищет

**По контрольной сумме** (ложных срабатываний практически нет): СНИЛС, ИНН
(10 и 12 знаков), полис ОМС, номер банковской карты.

**По формату + подтверждению по имени поля**: паспорт РФ, загранпаспорт,
водительское удостоверение, банковский счёт, почтовый индекс. У этих данных
контрольной суммы нет, поэтому одного формата недостаточно — иначе любая
колонка десятизначных кодов попадала бы в отчёт как паспорт.

**По значениям**: адрес электронной почты, телефон, адрес, ФИО целиком и по
частям, дата рождения.

**По свободному тексту (NER)**: ФИО и населённые пункты в комментариях,
описаниях, примечаниях — там, где ПДн заводятся незаметно и в реестр никогда
не попадают.

**По именам полей и комментариям**: специальные категории по ст. 10 152-ФЗ
(здоровье, диагнозы и МКБ, инвалидность, национальность, раса, религия,
политические взгляды, судимость, профсоюз), место рождения, свидетельство о
рождении и **сведения о родственниках** — они помечаются отдельно как ПДн
третьих лиц, поскольку согласия на их обработку обычно нет.

**Внутри JSON**: значение разбирается рекурсивно, каждый ключ становится
виртуальной колонкой. В отчёте это выглядит как `payload::$.client.phone` —
видно не только что в колонке есть ПДн, но и где именно внутри структуры.

## Как считается уверенность

Свидетельства независимы и складываются:

```
score = (доля значений выборки, совпавших с правилом) × вес правила
        + 0.35, если сработало имя поля или комментарий к нему
```

* **≥ 70 %** — ПДн, попадает в лёгкий отчёт и в реестр;
* **35–70 %** — требует ручной проверки;
* **< 35 %** — в отчёт не выносится.

Спецкатегории и родственники определяются только по именам полей: имена там
однозначные (`diagnosis`, `emergency_contact`), а цена пропуска высокая —
поэтому непустое поле сразу считается ПДн, пустое уходит на проверку.

## Что делается для безопасности прода

* `COUNT(*)` не выполняется никогда — размер берётся из `information_schema` /
  `system.tables`;
* одна выборка на таблицу, а не по запросу на колонку;
* значения обрезаются **на стороне сервера** (`LEFT(CAST(...))`,
  `substring(toString(...))`) — по сети не едут мегабайтные тексты;
* жёсткий таймаут запроса и ограничение `max_threads`;
* никаких `ORDER BY RAND()` — только `LIMIT`;
* `Distributed`, `Merge` и представления в ClickHouse пропускаются: иначе одни
  и те же данные попадут в отчёт по нескольку раз;
* примеры значений в отчётах маскируются (`ив****@ex***e.com`), иначе отчёт сам
  становится носителем ПДн. Флаг `--show-values` это отключает — пользоваться
  осознанно.

## Индикатор выполнения

В терминале сканер рисует полосу с текущей таблицей, процентом и оценкой
оставшегося времени:

```
prod-mysql [████████░░░░░░░░░░░░░░░░] 59/286  21% · осталось ~4 с  big.orders_2020_11
```

Полоса появляется только когда вывод идёт в терминал. В cron, systemd или
`docker run` без `-t` вместо неё пишутся редкие отметки в журнал (каждые 5%),
чтобы не плодить тысячи строк. Управляется ключом
`--progress auto|on|off`.

Команда `pii-scan`, поставленная установщиком, сама добавляет `-t` при
запуске из терминала. Если запускаете `docker run` руками — не забудьте флаг,
иначе индикатора не будет.

## Ключи запуска

```
--config PATH             путь к конфигу (в контейнере /config/config.yml)
--out DIR                 каталог отчётов (по умолчанию /out)
--formats СПИСОК          summary,detailed,json,xlsx или all
--dry-run                 только схема, значения не читаются
--limit N                 строк выборки на таблицу
--strategy head|tail|head_tail   откуда брать выборку
--only ИМЯ                только указанный источник (можно повторять)
--no-ner                  отключить NER по свободному тексту
--no-json                 не разбирать JSON внутри значений
--allow-rw                разрешить учётную запись с правами на запись
--show-values             не маскировать примеры (отчёт станет носителем ПДн)
--progress auto|on|off    индикатор выполнения
-q / -v                   тише / подробнее

Ограничение нагрузки:
--pause-ms МС             пауза между запросами к БД
--max-qpm N               не больше N запросов в минуту
--max-minutes МИН         бюджет времени на прогон
--no-grouping             не наследовать результат на однотипные таблицы
```

Полный список — `pii-scan --help`.

Коды возврата: `0` — успех, `1` — были ошибки при сканировании, `2` — ошибка
конфигурации, `3` — запуск заблокирован из-за прав на запись.

## Большие базы и сложные схемы

Стоимость прогона определяется не гигабайтами, а числом объектов: 50 ГБ в
двадцати таблицах — это двадцать запросов, те же 50 ГБ в пяти тысячах
партиций — пять тысяч. Поэтому масштабирование идёт по объектам.

**Однотипные таблицы обследуются по образцу.** `orders_2016_01 … orders_2025_12`
или `sessions_shard_00 … shard_63` — одна структура. Сканер группирует их по
имени с точностью до чисел **и по совпадению набора полей**, читает пару самых
крупных представителей, а остальным переносит объединённый результат с пометкой
«по образцу» в отчёте. Отключается флагом `--no-grouping`.

**Вероятное обследуется первым.** Таблицы, где имена полей уже намекают на ПДн,
идут в начале очереди. Если прогон оборвётся по времени, в отчёт успеет попасть
именно то, ради чего он запускался.

**Широкие таблицы читаются мельче.** Выборка ограничивается не числом строк, а
трафиком: `max_bytes_per_table` (по умолчанию 2 МБ). У таблицы на 300 колонок
сканер сам возьмёт меньше строк вместо десятков мегабайт по сети.

### Замеры на стенде

285 таблиц, 1277 колонок в MySQL (120 помесячных партиций, 64 шарда,
100 справочников, таблица на 120 колонок) плюс ClickHouse:

| Режим | Обследовано таблиц | Время |
|---|---|---|
| Без группировки | 290 из 290 | 18.8 с |
| С группировкой (по умолчанию) | **12 из 290**, остальные по образцу | 10.5 с |
| Пауза 200 мс между запросами | 12 | 13.2 с |
| Бюджет 1 мин, пауза 300 мс, без группировки | 188 из 290, остановлен по времени | 67 с |

Во всех четырёх режимах найден один и тот же набор таблиц с ПДн — включая
прогон, оборванный по бюджету: приоритизация вывела нужное вперёд, а
пропущенными оказались справочники без персональных данных.

## Ограничение нагрузки на прод

Главная опасность для работающей базы — не процессор, а вымывание буферного
пула: сканер читает первые страницы каждой таблицы, и они вытесняют горячие
данные приложения. Сдерживать это можно тремя способами.

```yaml
throttle:
  pause_ms: 200               # пауза между запросами
  max_queries_per_minute: 60  # либо потолок темпа
  max_duration_min: 30        # бюджет времени: по исчерпании прогон
                              # завершается корректно и сохраняет найденное
```

Те же параметры доступны ключами `--pause-ms`, `--max-qpm`, `--max-minutes`.

Дополнительно у каждого источника есть проброс настроек сессии — это точное
управление уже средствами самой СУБД:

```yaml
sources:
  - name: prod-clickhouse
    type: clickhouse
    settings:
      max_bytes_to_read: 100000000        # жёсткий потолок чтения на запрос
      max_execution_speed_bytes: 20000000 # родное ограничение скорости, байт/с
      max_memory_usage: 1000000000
      priority: 10                        # фоновый приоритет запросов

  - name: prod-mysql
    type: mysql
    settings:
      max_execution_time: 5000            # мс
```

Рекомендуемый порядок на проде:

1. `--dry-run` — только схема, ни одной строки данных. Уже покажет
   спецкатегории и родственников.
2. Полный прогон на **реплике**, если она есть, — там вымывание кэша никому
   не мешает.
3. Если реплики нет — ночное окно, `--pause-ms 200 --max-minutes 60` и
   `--limit 200`. Прогон, оборванный по бюджету, не теряет результат.



* Инструмент работает по **выборке** (по умолчанию 500 строк с начала таблицы).
  Редкие ПДн в конце большой таблицы он не увидит — увеличивайте `--limit` для
  подозрительных таблиц точечно.
* Спецкатегории и родственники определяются по именам полей. Поле
  `field_23`, в котором лежат диагнозы, не будет найдено, пока в схеме нет
  комментария.
* Контрольная сумма отсекает подавляющее большинство мусора, но около 1/11
  случайных десятизначных чисел формально проходят проверку ИНН. Гасится это
  долей совпадений по колонке: одно валидное значение из трёхсот находкой не
  становится.
* Кириллица в MySQL, записанная через соединение с неверной кодировкой
  (`Ð“Ð¾Ð»ÑƒÐ±ÐµÐ²` вместо `Голубев`), распознаётся и восстанавливается для
  анализа — иначе в legacy-базе сканер молча пропустил бы все ФИО и адреса.
  В отчёт при этом добавляется предупреждение: саму базу это не чинит.
* Результат — **основание для проверки, а не юридическая квалификация**.
  Решение об отнесении сведений к персональным данным принимает оператор.

## Тестовый стенд

Для проверки инструмента есть генератор синтетических данных — вымышленные
ФИО и адреса, валидные по контрольным суммам СНИЛС/ИНН/ОМС/карты, ПДн внутри
JSON и в свободном тексте, плюс намеренные ловушки на ложные срабатывания
(технические коды, журналы, метрики, настройки).

```bash
cd testdata && python generate.py . && docker compose -f docker-compose.test.yml up -d
```

Поднимутся MySQL с базой `crm` и ClickHouse с базой `analytics` в сети
`pii-test-net`, вместе с учётными записями `pii_reader` (только чтение) и
`app_rw` / `etl_writer` (с правами на запись — для проверки блокировки).
Сканер запускается в той же сети:

```bash
docker run --rm --network pii-test-net --user "$(id -u):$(id -g)" -v "$PWD/config:/config:ro" -v "$PWD/out:/out" -e MYSQL_PWD='ReadOnly_2026!' -e CH_PWD='ReadOnly_2026!' pii-scan:full --config /config/config.yml
```
